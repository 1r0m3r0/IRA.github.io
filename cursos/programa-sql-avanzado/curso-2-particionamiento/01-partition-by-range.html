📅 PARTITION BY RANGE

Divide tus datos por rangos: fechas, IDs, precios

💡 Piénsalo así: PARTITION BY RANGE es como organizar un archivo de recibos por año. En vez de tener todos los recibos mezclados en una caja enorme (tabla única), pones los de 2022 en una carpeta, los de 2023 en otra, etc. Cuando necesitas los recibos de 2024, solo abres esa carpeta. No buscas en toda la caja.

  • La diferencia entre particionamiento físico (tablas separadas) y lógico (misma tabla padre)
  • Buenas prácticas para elegir el tamaño de rango óptimo según el volumen de datos

Sintaxis Básica

CREATE TABLE padre (...) PARTITION BY RANGE (columna); define la tabla particionada. Luego cada partición se crea con PARTITION OF padre FOR VALUES FROM (min) TO (max). Los rangos son inclusivos en el límite inferior y exclusivos en el superior.

CREATE TABLE ventas (id INT, fecha DATE, total NUMERIC) PARTITION BY RANGE (fecha); CREATE TABLE ventas_2024 PARTITION OF ventas FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

La tabla padre no almacena datos directamente; solo define la estructura y las reglas de enrutamiento. Cada partición hija es una tabla física independiente con su propio storage.

⚠ El rango FROM es inclusive, TO es exclusive. FROM '2024-01-01' TO '2025-01-01' incluye todo 2024

Enrutamiento Automático

Cuando insertas una fila, PostgreSQL calcula automáticamente a qué partición debe ir según el valor de la columna de partición. Si el valor cae dentro del rango de una partición existente, la fila se inserta allí. Esto es transparente para la aplicación.

INSERT INTO ventas VALUES (1, '2024-06-15', 100.50); -- Va a ventas_2024 automáticamente

El enrutamiento usa el mismo mecanismo de constraint exclusion. Cada partición tiene CHECK constraints implícitos que definen su rango, y PostgreSQL los usa para dirigir la inserción.

⚠ Si insertas un valor fuera de todos los rangos definidos, PostgreSQL lanza error

Particiones por Fecha

El caso de uso más común: particionar por año, mes o día. Las tablas de logs, facturación y eventos temporales se benefician enormemente. Puedes eliminar particiones antiguas (DROP TABLE) sin afectar datos recientes y archivar datos viejos.

CREATE TABLE logs_2024_01 PARTITION OF logs FOR VALUES FROM ('2024-01-01') TO ('2024-02-01'); CREATE TABLE logs_2024_02 PARTITION OF logs FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

Para datos mensuales, cada partición tiene ~1 mes de datos. Si un mes tiene 10M filas, el escaneo de ese mes solo lee 10M filas en vez de 120M (un año completo).

⚠ Crea particiones futuras con anticipación. Un cron job puede crearlas automáticamente

Particiones por ID

También puedes particionar por rangos numéricos como IDs. Útil para tablas con IDs secuenciales donde los datos nuevos se insertan al final. Cada partición puede tener un rango de IDs, facilitando el archive de IDs antiguos.

CREATE TABLE pedidos (id INT, ...) PARTITION BY RANGE (id); CREATE TABLE pedidos_old PARTITION OF pedidos FOR VALUES FROM (1) TO (1000000); CREATE TABLE pedidos_new PARTITION OF pedidos FOR VALUES FROM (1000000) TO (2000000);

Las consultas por rango de IDs también se benefician del partition pruning: WHERE id BETWEEN 500000 AND 600000 solo escanea la partición relevante.

⚠ Si usas SERIAL, los IDs se agotan. Planifica el máximo de IDs por partición

Default Partition

PostgreSQL permite crear una partición DEFAULT que captura todos los valores que no caen en ninguna partición definida. Útil como red de seguridad para evitar errores de inserción, pero puede ocultar configuraciones incorrectas.

CREATE TABLE ventas_default PARTITION OF ventas DEFAULT;

La partición DEFAULT debe usarse con cuidado: si acumula datos accidentalmente, el partition pruning no funciona con ella. Es mejor monitorear su tamaño regularmente y crear particiones faltantes.

⚠ Si la partición DEFAULT crece demasiado, las consultas que no usan filtro de partición pueden escanearla innecesariamente

Tamaño de Rango Óptimo

El tamaño de cada partición depende del volumen de datos y la frecuencia de consultas. Regla general: cada partición debe tener entre 1M y 10M filas. Demasiadas particiones pequeñas aumentan el overhead de planificación; muy pocas particiones grandes reducen el beneficio del pruning.

-- Para 100M filas/año: 12 particiones mensuales (~8M c/u) es óptimo CREATE TABLE ventas_2024_01 ... FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

PostgreSQL 19 permite hasta 32,767 particiones por tabla, pero el planificador debe revisar cada una durante la planificación. Más de 500-1000 particiones puede ralentizar la planificación.

⚠ No crees más de 500-1000 particiones por tabla a menos que el partition pruning elimine la mayoría

Ejemplo paso a paso

1

Creamos una tabla particionada por rango de fechas para ventas

CREATE TABLE ventas (id SERIAL, fecha DATE NOT NULL, total NUMERIC, region TEXT) PARTITION BY RANGE (fecha);
2

Agregamos particiones mensuales para los primeros 3 meses de 2024

CREATE TABLE ventas_2024_01 PARTITION OF ventas FOR VALUES FROM ('2024-01-01') TO ('2024-02-01'); CREATE TABLE ventas_2024_02 PARTITION OF ventas FOR VALUES FROM ('2024-02-01') TO ('2024-03-01'); CREATE TABLE ventas_2024_03 PARTITION OF ventas FOR VALUES FROM ('2024-03-01') TO ('2024-04-01');
3

Insertamos datos; PostgreSQL enruta automáticamente cada fila a su partición

INSERT INTO ventas (fecha, total, region) VALUES ('2024-01-15', 150.00, 'Norte'), ('2024-02-20', 200.00, 'Sur'), ('2024-03-10', 75.50, 'Este'); -- Cada fila va a la partición correspondiente según su fecha
4

Consultamos con filtro por fecha; el partition pruning solo escanea la partición relevante

EXPLAIN SELECT * FROM ventas WHERE fecha = '2024-02-20'; -- Solo escanea ventas_2024_02, ignora las demás particiones
5

Podemos eliminar particiones antiguas sin afectar los datos actuales (DROP TABLE es instantáneo)

DROP TABLE ventas_2024_01; -- Elimina todos los datos de enero 2024 al instante -- Mucho más rápido que DELETE FROM ventas WHERE fecha BETWEEN '2024-01-01' AND '2024-01-31'

Constructor de particiones por rango

🔹 CREATE TABLE orders (id INT, created_at DATE, total NUMERIC) PARTITION BY RANGE (created_at);

💬 Observa cómo los datos se distribuyen en particiones por año. Cada partición es una tabla separada físicamente.

Resumen del módulo

  • PARTITION BY RANGE divide datos en rangos contiguos: fechas, IDs, montos
  • Cada partición es una tabla física independiente con CHECK constraints implícitos
  • El enrutamiento es automático y transparente: INSERT dirige a la partición correcta
  • El partition pruning elimina particiones irrelevantes en consultas con filtro por rango
  • DROP TABLE de una partición es instantáneo vs DELETE masivo que genera bloat
  • Planifica particiones futuras y monitorea la partición DEFAULT para detectar configuraciones incorrectas
