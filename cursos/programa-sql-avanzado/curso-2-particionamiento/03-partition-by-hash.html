#️⃣ PARTITION BY HASH

Distribuye uniformemente con hashing

💡 Piénsalo así: PARTITION BY HASH es como repartir estudiantes en aulas según los últimos dígitos de su carnet. El hash garantiza que cada aula tenga ~el mismo número de estudiantes, sin importar el orden alfabético o la fecha. Es la opción justa cuando no hay un criterio natural de partición.

Función Hash

PostgreSQL usa una función hash interna para calcular el remainder de la columna de partición. La fórmula es: hash(value) % N = remainder. Cada partición se define con un módulo (N) y un remainder (R). Los valores con el mismo remainder van a la misma partición.

CREATE TABLE pedidos (id INT, cliente TEXT, total NUMERIC) PARTITION BY HASH (id); CREATE TABLE pedidos_p0 PARTITION OF pedidos FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE pedidos_p1 PARTITION OF pedidos FOR VALUES WITH (MODULUS 4, REMAINDER 1);

Todas las particiones deben usar el mismo MODULUS. Cambiar el número de particiones requiere recrear la tabla con un nuevo MODULUS.

⚠ No puedes agregar particiones HASH individualmente como en RANGE; todas deben compartir el mismo MODULUS

Distribución Uniforme

La principal ventaja de HASH es que distribuye los datos uniformemente entre las particiones, sin importar la distribución real de los valores. Ideal para columnas sin orden natural (UUIDs, hashes, tokens) o cuando no hay un criterio de partición obvio.

-- Con 4 particiones, cada una recibe ~25% de los datos INSERT INTO pedidos SELECT generate_series(1,10000), 'cliente_' || n, random()*1000; -- Cada partición tendrá ~2500 filas

La desviación típica entre particiones es muy baja (<5%). Esto evita hotspots donde una partición tiene muchos más datos que las otras.

⚠ HASH no permite partition pruning basado en rangos o listas; las consultas sin filtro exacto escanean todas las particiones

Cuándo Usar HASH

HASH es ideal cuando: (1) no hay una columna con orden natural para RANGE, (2) la columna tiene alta cardinalidad (IDs, UUIDs), (3) necesitas distribución uniforme para carga de trabajo de escritura intensiva, (4) las consultas siempre incluyen un filtro exacto por la clave de partición.

-- Buen caso: particionar por user_id en un sistema SaaS CREATE TABLE events (user_id UUID, event TEXT, ts TIMESTAMP) PARTITION BY HASH (user_id);

Ejemplo real: sistemas de eventos, logs con IDs únicos, tablas de usuarios donde cada consulta filtra por user_id exacto.

⚠ HASH es inútil para consultas por rango (WHERE fecha BETWEEN ...). Para eso usa RANGE.

HASH vs RANGE vs LIST

RANGE: orden natural, partition pruning por rangos. LIST: valores discretos, partition pruning por igualdad. HASH: distribución uniforme, partition pruning solo por igualdad exacta. La elección depende del patrón de consultas dominante.

-- RANGE: bueno para reports por período SELECT sum(total) FROM ventas WHERE fecha >= '2024-01-01' AND fecha < '2024-02-01'; -- HASH: bueno para búsqueda puntual SELECT * FROM usuarios WHERE user_id = 'abc-123';

Si el 80% de las consultas usan filtro por user_id exacto, HASH es ideal. Si las consultas son por rangos de fecha, prefiere RANGE.

⚠ HASH requiere consultas con filtro exacto en la clave de partición para beneficiarse del pruning

Cambio de Particiones

Si necesitas cambiar de 4 a 8 particiones HASH, debes recrear toda la tabla: CREATE TABLE nuevo_con_MODULUS_8, INSERT INTO nuevo SELECT * FROM viejo, DROP TABLE viejo, RENAME. Esto puede tomar tiempo y requiere planificación.

-- No puedes simplemente agregar una partición con MODULUS 8 -- Debes recrear la tabla completa CREATE TABLE pedidos_new (LIKE pedidos) PARTITION BY HASH (id); CREATE TABLE pedidos_p0 NEW PARTITION OF pedidos_new FOR VALUES WITH (MODULUS 8, REMAINDER 0); -- ... y así hasta 7 INSERT INTO pedidos_new SELECT * FROM pedidos; DROP TABLE pedidos; ALTER TABLE pedidos_new RENAME TO pedidos;

Por eso es importante elegir bien el número inicial de particiones. En PostgreSQL 19 no hay MERGE/SPLIT para HASH (solo para RANGE).

⚠ Planea el número de particiones HASH con margen de crecimiento futuro. No podrás aumentarlo sin recrear la tabla.

Casos de Uso Reales

HASH se usa en sistemas multi-tenant (cada tenant_id va a una partición), colas de mensajes (distribución uniforme de carga), tablas de sesiones (UUIDs), y cualquier sistema donde la clave de partición tenga alta cardinalidad y las consultas sean por igualdad.

-- SaaS multi-tenant: cada tenant en una partición CREATE TABLE orders (tenant_id INT, order_data JSONB) PARTITION BY HASH (tenant_id); -- Cola de trabajo CREATE TABLE job_queue (job_id UUID, payload JSONB) PARTITION BY HASH (job_id);

En sistemas de colas, HASH garantiza que ningún worker tenga más trabajo que otro. Cada worker puede procesar una o más particiones.

⚠ No uses HASH para tablas pequeñas (<1M filas). El overhead de planificación no justifica la partición.

Ejemplo paso a paso

1

Creamos una tabla de eventos particionada por HASH con 4 particiones

CREATE TABLE events (id BIGSERIAL, user_id INT, event TEXT, ts TIMESTAMP) PARTITION BY HASH (user_id); CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE events_p1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1); CREATE TABLE events_p2 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 2); CREATE TABLE events_p3 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 3);
2

Insertamos 10,000 eventos de prueba; cada user_id se distribuye por hash

INSERT INTO events (user_id, event, ts) SELECT (random()*1000)::int, 'login', now() - (random()*365 || ' days')::interval FROM generate_series(1,10000);
3

Verificamos la distribución uniforme entre las 4 particiones

SELECT 'p0' AS part, count(*) FROM events_p0 UNION ALL SELECT 'p1', count(*) FROM events_p1 UNION ALL SELECT 'p2', count(*) FROM events_p2 UNION ALL SELECT 'p3', count(*) FROM events_p3; -- Cada una debería tener ~2500 filas
4

Consultamos por user_id exacto; partition pruning escanea solo 1 partición

EXPLAIN SELECT * FROM events WHERE user_id = 42; -- Solo escanea la partición cuyo remainder es hash(42) % 4
5

Si consultamos por rango de fechas SIN filtro de user_id, se escanean todas las particiones (sin pruning)

EXPLAIN SELECT count(*) FROM events WHERE ts >= '2024-01-01'; -- Escanea las 4 particiones porque no hay filtro por user_id

Resumen del módulo

  • PARTITION BY HASH usa hash(value) % N para distribuir datos uniformemente entre N particiones
  • Ideal para columnas de alta cardinalidad sin orden natural (UUIDs, IDs)
  • Garantiza distribución uniforme (<5% desviación), evitando hotspots
  • El partition pruning solo funciona con filtros exactos (WHERE col = X), no con rangos
  • Cambiar el número de particiones (MODULUS) requiere recrear toda la tabla
  • Úsalo para sistemas multi-tenant, colas, sesiones, y cargas de escritura intensiva
