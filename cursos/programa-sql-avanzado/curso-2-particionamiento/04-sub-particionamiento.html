🌳 Sub-Particionamiento

Particiones dentro de particiones

💡 Piénsalo así: Sub-particionar es como tener un archivador de oficina: primero separas por año (RANGE) y dentro de cada año, separas por mes (otro RANGE más fino). O por departamento (LIST). Así no solo sabes en qué año buscar, sino en qué mes exacto. Menos espacio que revisar.

  • Cuándo el sub-particionamiento mejora el rendimiento y cuándo empeora

Jerarquía RANGE + LIST

El sub-particionamiento más común: primero RANGE por fecha (año), luego LIST por región o categoría. Esto permite consultas eficientes por año y por región simultáneamente. PostgreSQL soporta hasta 32,767 sub-particiones totales.

CREATE TABLE pedidos (id INT, fecha DATE, region TEXT, total NUMERIC) PARTITION BY RANGE (fecha); CREATE TABLE pedidos_2024 PARTITION OF pedidos FOR VALUES FROM ('2024-01-01') TO ('2025-01-01') PARTITION BY LIST (region); -- Sub-partición por LIST

Cada partición de año se convierte en una tabla padre para sus sub-particiones de región. Los CHECK constraints se heredan y combinan.

⚠ Cada nivel de sub-participación añade overhead de planificación. No abuses con más de 2-3 niveles

Jerarquía RANGE + RANGE

También puedes sub-particionar por RANGE dentro de RANGE. Ejemplo: primero por año, luego por mes. Esto da granularidad fina para consultas temporales. Cada sub-participación mensual está contenida dentro de su partición anual.

CREATE TABLE logs (id INT, ts TIMESTAMP, mensaje TEXT) PARTITION BY RANGE (ts); CREATE TABLE logs_2024 PARTITION OF logs FOR VALUES FROM ('2024-01-01') TO ('2025-01-01') PARTITION BY RANGE (ts); -- Sub-partición mensual CREATE TABLE logs_2024_01 PARTITION OF logs_2024 FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

Las consultas con WHERE ts BETWEEN '2024-01-15' AND '2024-01-31' primero podan al año 2024, luego al mes enero.

⚠ Asegúrate de que los rangos de sub-partición no se solapen. Las sub-particiones deben respetar el rango de la partición padre.

Particiones por Defecto y Sub-partición

Puedes tener una partición DEFAULT que a su vez esté sub-particionada. Esto captura valores no clasificados en el nivel superior pero aún así los organiza internamente. Sin embargo, el partition pruning es menos efectivo con DEFAULT.

CREATE TABLE pedidos_default PARTITION OF pedidos DEFAULT PARTITION BY LIST (region); -- DEFAULT también sub-particionada CREATE TABLE pedidos_default_otras PARTITION OF pedidos_default FOR VALUES IN ('OT', 'NA');

La sub-partición de DEFAULT permite al menos organizar los datos no clasificados, aunque el pruning a nivel superior no funcionará con ellos.

⚠ Monitorea el tamaño de las particiones DEFAULT. Si crecen mucho, es mejor crear particiones explícitas.

Límite de 32,767 Particiones

PostgreSQL 19 permite hasta 32,767 particiones por tabla (contando todos los niveles jerárquicos). Este límite es tanto de almacenamiento como de planificación: el optimizador debe evaluar los CHECK constraints de cada partición durante la planificación.

-- 10 años × 50 regiones = 500 sub-particiones (bien) -- 100 años × 328 regiones = 32,800 (excede el límite) -- 5 años × 12 meses × 50 regiones = 3,000 (aceptable)

El límite práctico recomendado es mucho menor: 500-1000 particiones. Más allá de eso, la planificación puede tomar segundos adicionales por consulta.

⚠ Más de 1000 particiones ralentiza EXPLAIN y la planificación de consultas. Mantén el diseño simple.

Partition Pruning Multi-nivel

El partition pruning trabaja en todos los niveles de la jerarquía. Si tienes RANGE(año) + LIST(región), y consultas WHERE fecha BETWEEN '2024-06-01' AND '2024-06-30' AND region = 'ES', PostgreSQL poda primero al año 2024 y luego a la sub-partición de Europa.

EXPLAIN SELECT * FROM pedidos WHERE fecha = '2024-06-15' AND region = 'ES'; -- Nivel 1: poda a pedidos_2024 (solo año 2024) -- Nivel 2: poda a pedidos_2024_europa (solo región ES)

Cada nivel de pruning requiere un filtro en la columna de partición de ese nivel. Si falta el filtro de región, se escanean todas las sub-particiones del año.

⚠ Sin filtro en todos los niveles, el pruning no es completo. Diseña consultas que incluyan todas las columnas de partición.

Buenas Prácticas

No sub-particiones sin necesidad. Dos niveles suelen ser suficientes: RANGE (año) + LIST (región) o RANGE (año) + RANGE (mes). Tres niveles ya son excesivos para la mayoría de casos. Mide el rendimiento real antes de agregar más niveles.

-- Buen diseño: 2 niveles CREATE TABLE ventas (fecha DATE, region TEXT, total NUMERIC) PARTITION BY RANGE (fecha) SUBPARTITION BY LIST (region); -- PostgreSQL no tiene SUBPARTITION. Esto es conceptual.

Regla: cada nivel debe eliminar al menos el 90% de las particiones del nivel anterior. Si no, el overhead del nivel no se justifica.

⚠ El sub-particionamiento añade complejidad al mantenimiento. Cada nivel requiere crear y gestionar más objetos.

Ejemplo paso a paso

1

Creamos una tabla con sub-particionamiento: RANGE por año + LIST por región

CREATE TABLE ventas (id INT, fecha DATE, region TEXT, total NUMERIC) PARTITION BY RANGE (fecha); CREATE TABLE ventas_2024 PARTITION OF ventas FOR VALUES FROM ('2024-01-01') TO ('2025-01-01') PARTITION BY LIST (region); CREATE TABLE ventas_2025 PARTITION OF ventas FOR VALUES FROM ('2025-01-01') TO ('2026-01-01') PARTITION BY LIST (region);
2

Creamos las sub-particiones LIST dentro de cada año

CREATE TABLE ventas_2024_america PARTITION OF ventas_2024 FOR VALUES IN ('US', 'CA', 'MX'); CREATE TABLE ventas_2024_europa PARTITION OF ventas_2024 FOR VALUES IN ('ES', 'FR', 'DE'); CREATE TABLE ventas_2024_asia PARTITION OF ventas_2024 FOR VALUES IN ('JP', 'CN', 'KR'); CREATE TABLE ventas_2025_america PARTITION OF ventas_2025 FOR VALUES IN ('US', 'CA', 'MX'); CREATE TABLE ventas_2025_europa PARTITION OF ventas_2025 FOR VALUES IN ('ES', 'FR', 'DE'); CREATE TABLE ventas_2025_asia PARTITION OF ventas_2025 FOR VALUES IN ('JP', 'CN', 'KR');
3

Insertamos datos; PostgreSQL enruta a nivel año y luego a nivel región

INSERT INTO ventas VALUES (1, '2024-06-15', 'ES', 150.00); -- ventas_2024 → ventas_2024_europa INSERT INTO ventas VALUES (2, '2025-01-10', 'JP', 200.00); -- ventas_2025 → ventas_2025_asia
4

Consultamos con filtros en ambos niveles; pruning multi-nivel activo

EXPLAIN SELECT * FROM ventas WHERE fecha = '2024-06-15' AND region = 'ES'; -- Nivel 1: poda a ventas_2024 -- Nivel 2: poda a ventas_2024_europa
5

Verificamos la estructura jerárquica en pg_partition_tree

SELECT * FROM pg_partition_tree('ventas'); -- Muestra: ventas → ventas_2024 → ventas_2024_europa -- Cada nivel es una tabla física independiente

Resumen del módulo

  • Sub-particionar es crear particiones dentro de particiones, formando una jerarquía de tablas
  • Los patrones más comunes: RANGE + LIST (año + región) y RANGE + RANGE (año + mes)
  • PostgreSQL 19 permite hasta 32,767 particiones totales; el límite práctico es ~500-1000
  • El partition pruning trabaja en todos los niveles jerárquicos, pero requiere filtros en cada columna de partición
  • Cada nivel añade overhead de planificación; 2 niveles suele ser suficiente
  • La partición DEFAULT también puede sub-particionarse para organizar datos no clasificados
