🔗 ATTACH / DETACH

Agrega y remueve particiones sin downtime

💡 Piénsalo así: ATTACH/DETACH es como agregar o quitar un vagón de un tren en movimiento. ATTACH CONCURRENTLY añade un nuevo vagón mientras el tren sigue andando. DETACH CONCURRENTLY desconecta un vagón sin parar el tren. Nadie nota el cambio, pero la composición cambió.

ATTACH Básico

ATTACH PARTITION agrega una tabla existente como nueva partición de una tabla particionada. La tabla debe tener los CHECK constraints correctos que definan el rango/lista de valores que contiene. PostgreSQL verifica que los datos cumplan con el constraint antes de completar el ATTACH.

CREATE TABLE ventas_2026 (LIKE ventas INCLUDING DEFAULTS); INSERT INTO ventas_2026 SELECT * FROM ventas_staging WHERE fecha >= '2026-01-01'; ALTER TABLE ventas ATTACH PARTITION ventas_2026 FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

Durante el ATTACH, PostgreSQL valida que todas las filas de la tabla cumplan el rango. Esto puede tomar tiempo en tablas grandes, pero no bloquea la tabla padre para consultas SELECT.

⚠ ATTACH adquiere un ACCESS EXCLUSIVE LOCK breve para validar y luego otro para agregar. En tablas grandes (>100M filas), programa en ventana de mantenimiento.

ATTACH CONCURRENTLY

Desde PostgreSQL 18, ATTACH CONCURRENTLY permite agregar una partición sin bloquear escrituras concurrentes. PostgreSQL 19 mejora aún más este proceso reduciendo la ventana de bloqueo al mínimo. Es la opción recomendada para producción.

ALTER TABLE ventas ATTACH PARTITION CONCURRENTLY ventas_2026 FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

CONCURRENTLY funciona en dos fases: (1) valida los datos sin bloqueo exclusivo, (2) intercambia metadatos atómicamente. Durante la validación, las inserciones y consultas continúan normalmente.

⚠ ATTACH CONCURRENTLY requiere más CPU y memoria para la validación, pero el tradeoff vale la pena para sistemas 24/7

DETACH

DETACH PARTITION desconecta una partición de la tabla padre. La partición se convierte en una tabla independiente con todos sus datos intactos. No se pierde nada. Útil para archivar datos antiguos, migrar datos a otro sistema, o reparar particiones corruptas.

ALTER TABLE ventas DETACH PARTITION ventas_2022; -- ventas_2022 ahora es una tabla normal con sus datos SELECT count(*) FROM ventas_2022; -- Sigue funcionando

Después de DETACH, la tabla independiente puede renombrarse, moverse a otro tablespace, o eliminarse. Si quieres eliminar los datos definitivamente, usa DROP TABLE después.

⚠ DETACH adquiere ACCESS EXCLUSIVE LOCK. Usa DETACH CONCURRENTLY (PG18+) para sistemas con alta concurrencia

Validación Antes de ATTACH

Antes de ATTACH, debes asegurarte de que la tabla candidata cumple con el esquema de la partición. La tabla debe tener las mismas columnas, tipos y restricciones. Puedes usar LIKE para crear la estructura idéntica y luego validar con CHECK constraints explícitos.

-- Verificar que los datos están en el rango correcto ALTER TABLE ventas_2026 ADD CHECK (fecha >= '2026-01-01' AND fecha < '2027-01-01'); -- Ahora PostgreSQL confía en el CHECK y no necesita validar durante ATTACH (más rápido) ALTER TABLE ventas ATTACH PARTITION ventas_2026 FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

Si la tabla ya tiene un CHECK constraint que cubre exactamente el rango de la partición, PostgreSQL omite la validación de datos durante ATTACH, haciéndolo instantáneo.

⚠ Siempre agrega CHECK constraints a la tabla candidata antes de ATTACH para que la operación sea instantánea

Migración de Datos Históricos

ATTACH es ideal para migrar datos históricos a una tabla particionada sin downtime. Puedes crear la tabla particionada, luego ATTACH los datos existentes lote por lote. Esto es más rápido que INSERT masivo porque ATTACH solo mueve metadatos.

-- 1. Crear tabla vacía particionada CREATE TABLE ventas (LIKE ventas_old) PARTITION BY RANGE (fecha); -- 2. Crear particiones para cada año CREATE TABLE ventas_2020 (LIKE ventas INCLUDING DEFAULTS); INSERT INTO ventas_2020 SELECT * FROM ventas_old WHERE fecha BETWEEN '2020-01-01' AND '2020-12-31'; ALTER TABLE ventas ATTACH PARTITION ventas_2020 FOR VALUES FROM ('2020-01-01') TO ('2021-01-01'); -- 3. Repetir para cada año

Este proceso puede hacerse en línea: primero particionas los datos más recientes, y luego vas agregando años anteriores progresivamente.

⚠ Durante la migración, las consultas a la tabla padre solo ven las particiones ATTACHED. Los datos no migrados aún no son visibles.

Estrategias de Particionamiento en Caliente

Para sistemas 24/7, la estrategia recomendada es: (1) pre-crear particiones futuras (próximos 3-6 meses), (2) rotar particiones viejas con DETACH a tablas de archive, (3) usar ATTACH CONCURRENTLY para agregar datos migrados. Todo sin afectar la operación.

-- Rotación mensual: -- Día 1 del mes: DETACH mes más antiguo, ATTACH mes nuevo (pre-creado) ALTER TABLE ventas DETACH PARTITION CONCURRENTLY ventas_2024_01; ALTER TABLE ventas ATTACH PARTITION CONCURRENTLY ventas_2026_01 FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

Automatiza este proceso con pg_cron o un job scheduler. Mantén siempre un margen de particiones futuras para no olvidar crearlas.

⚠ Monitorea el tamaño de las particiones. Si una crece desproporcionadamente, puede necesitar SPLIT (PG 19).

Ejemplo paso a paso

1

Creamos una tabla particionada y sus primeras particiones

CREATE TABLE logs (id BIGSERIAL, ts TIMESTAMP, evento TEXT) PARTITION BY RANGE (ts); CREATE TABLE logs_2024 PARTITION OF logs FOR VALUES FROM ('2024-01-01') TO ('2025-01-01'); CREATE TABLE logs_2025 PARTITION OF logs FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
2

Llega 2026 y necesitamos agregar la partición. Creamos la tabla primero con el CHECK constraint para ATTACH instantáneo

CREATE TABLE logs_2026 (LIKE logs INCLUDING DEFAULTS); ALTER TABLE logs_2026 ADD CHECK (ts >= '2026-01-01' AND ts < '2027-01-01'); -- Poblamos con datos de staging INSERT INTO logs_2026 SELECT * FROM logs_staging WHERE ts >= '2026-01-01';
3

ATTACH la nueva partición (con CHECK pre-existente, es instantáneo)

ALTER TABLE logs ATTACH PARTITION logs_2026 FOR VALUES FROM ('2026-01-01') TO ('2027-01-01'); -- Instantáneo porque el CHECK constraint ya valida los datos
4

Archivamos datos de 2024: DETACH la partición antigua

ALTER TABLE logs DETACH PARTITION logs_2024; -- logs_2024 ahora es una tabla normal. Podemos moverla a otro tablespace o comprimirla.
5

Verificamos que la tabla padre solo tiene las particiones activas

SELECT inhrelid::regclass FROM pg_inherits WHERE inhparent = 'logs'::regclass; -- Muestra: logs_2025, logs_2026 (logs_2024 ya no está)
