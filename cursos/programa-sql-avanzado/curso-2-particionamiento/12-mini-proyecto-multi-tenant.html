🏆 Mini-Proyecto Multi-Tenant

Diseña una arquitectura multi-tenant completa

💡 Piénsalo así: Un sistema multi-tenant es como un edificio de oficinas: cada empresa (tenant) tiene su propio espacio, sus datos y sus usuarios, pero comparten la infraestructura del edificio (el cluster de BD). Tu trabajo es diseñar cómo particionar los datos para que cada empresa tenga buen rendimiento sin interferir con las demás.

Diseño de Base de Datos Multi-Tenant

Existen tres enfoques: (1) una BD por tenant (aislamiento total, costoso de administrar), (2) una tabla por tenant (esquema dinámico, difícil de mantener), (3) tablas compartidas con tenant_id (eficiente, requiere shard key). El enfoque #3 es el estándar en SaaS moderno.

-- Enfoque #3: tablas compartidas con tenant_id CREATE TABLE orders ( tenant_id INT NOT NULL, id BIGSERIAL, ... PRIMARY KEY (tenant_id, id) -- ¡Shard key en la PK! ); SELECT citus_create_distributed_table('orders','tenant_id');

La clave está en incluir tenant_id en la PRIMARY KEY. Esto permite que Citus use colocation automática y que las consultas por tenant sean ultra rápidas. Nunca uses PK sin tenant_id en multi-tenant shardeado.

⚠ Incluir tenant_id en todas las PK y FK duplica el almacenamiento pero es necesario para routing eficiente.

Reference Tables para Datos Compartidos

Los datos que son globales (catálogos, configuraciones, planes de precios) deben ser reference tables en Citus o tablas unsharded en Vitess. Se replican en todos los shards/workers, permitiendo JOINs locales sin mover datos entre nodos.

-- Reference table: misma copia en todos los workers CREATE TABLE planes_precio (id INT, nombre TEXT, precio NUMERIC); SELECT citus_create_reference_table('planes_precio'); -- JOIN local con tabla distribuida SELECT o.*, p.nombre FROM orders o JOIN planes_precio p ON o.plan_id = p.id WHERE o.tenant_id = 101; -- JOIN local ✅

Las reference tables deben ser pequeñas (< 100k filas). Cada UPDATE se replica en todos los workers. Para datos medianos (100k-1M), considera tabla distribuida con shard key = id.

⚠ Las reference tables se replican sincrónicamente: cada escritura espera confirmación de todos los workers. No abuses de ellas.

Aislamiento y Seguridad por Tenant

El aislamiento entre tenants es crítico. Además de la shard key, implementa Row-Level Security (RLS) en PostgreSQL para que ningún tenant pueda leer datos de otro aunque la consulta no incluya tenant_id. Esto es defensa en profundidad.

-- RLS por tenant (capa extra de seguridad) ALTER TABLE orders ENABLE ROW LEVEL SECURITY; CREATE POLICY tenant_isolation ON orders USING (tenant_id = current_setting('app.tenant_id')::INT); -- Incluso si alguien consulta sin WHERE tenant_id=, RLS filtra

Combina RLS con sharding: RLS es la red de seguridad para errores humanos en queries. El sharding es la optimización de rendimiento. Ambos se complementan.

⚠ RLS tiene overhead en cada consulta. En sistemas con >10k queries/segundo, considera auditoría post-query en lugar de RLS.

Escalado: De 10 a 10,000 Tenants

Cuando empiezas con pocos tenants, un solo nodo basta. Al crecer, agregas workers y rebalanceas. La clave es diseñar para escalar desde el día 1: elige tenant_id como shard key, usa colocation, y monitorea el tamaño por shard para saber cuándo escalar.

-- Fase 1 (10 tenants): 1 nodo, sin sharding visible -- Fase 2 (100 tenants): 2 workers Citus, 4 shards -- Fase 3 (1000 tenants): 8 workers, 32 shards -- Fase 4 (10000+ tenants): 32+ workers, resharding periódico SELECT citus_add_node('worker-nuevo', 5432); SELECT citus_rebalance_start();

Monitorea: tamaño por shard (< 10 GB ideal), queries por segundo por worker, latencia P95, y skew de distribución. Cuando un worker supera 80% de CPU/RAM, agrega otro y rebalancea.

⚠ El rebalanceo mueve datos entre workers. En sistemas con >1 TB, programa rebalanceos semanales en ventanas de mantenimiento.

Migración desde BD Monolítica

Migrar una BD existente a multi-tenant shardeado requiere planificación. El patrón "shawshank" (migración gradual) es el más seguro: (1) crea la nueva tabla shardeada, (2) escribe en ambas durante un período, (3) mueve datos históricos con batch ATTACH, (4) corta el tráfico gradualmente.

-- Patrón shawshank: migración sin downtime -- 1. Crear tabla shardeada paralela SELECT citus_create_distributed_table('orders_new','tenant_id'); -- 2. Trigger bidireccional (escribe en ambas) CREATE FUNCTION sync_orders() RETURNS TRIGGER AS $$ BEGIN INSERT INTO orders_new VALUES (NEW.*); RETURN NEW; END; $$ LANGUAGE plpgsql; -- 3. Migrar datos antiguos en lotes INSERT INTO orders_new SELECT * FROM orders WHERE fecha < '2025-01-01'; -- 4. Cortar tráfico: renombrar tablas

El patrón shawshank permite migrar millones de filas con cero downtime. Los usuarios no notan la migración. Si algo sale mal, reviertes el rename.

⚠ Durante la migración, las escrituras tienen latencia extra por el trigger bidireccional. Monitorea para no saturar la BD origen.

Monitoreo y Operación Continua

Un cluster multi-tenant requiere monitoreo constante. Métricas clave: tamaño de shards (skew), queries scatter (sin shard key), conexiones por worker, replicación lag. Herramientas: pg_cron para tareas programadas, pg_stat_statements para queries lentas.

-- Monitoreo de skew: distribución por shard SELECT nodename, count(*) AS shards, sum(shard_size)::numeric/1e9 AS total_gb FROM citus_shard_sizes() GROUP BY nodename ORDER BY total_gb DESC; -- Alerta si un worker tiene >30% más datos que el promedio -- Monitoreo de scatter queries SELECT query, calls, total_time FROM pg_stat_statements WHERE query NOT LIKE '%tenant_id%' -- Posible scatter query ORDER BY total_time DESC LIMIT 10;

Automatiza alertas con Prometheus + Grafana o el sistema de monitoreo de tu cloud (CloudWatch, Azure Monitor). Define SLOs: latencia < 100ms P95, scatter queries < 5% del total.

⚠ Las scatter queries son el síntoma más común de degradación. Si crecen >10%, revisa si las consultas incluyen la shard key.

Ejemplo paso a paso

1

Creamos el esquema multi-tenant con tenant_id en todas las PK y configuramos Citus

CREATE TABLE tenants (id INT PRIMARY KEY, nombre TEXT, plan TEXT); CREATE TABLE orders (tenant_id INT, id BIGSERIAL, producto TEXT, total NUMERIC, fecha DATE, PRIMARY KEY (tenant_id, id)); CREATE TABLE invoices (tenant_id INT, id BIGSERIAL, order_id INT, monto NUMERIC, PRIMARY KEY (tenant_id, id)); SELECT citus_create_reference_table('tenants'); SELECT citus_create_distributed_table('orders','tenant_id'); SELECT citus_create_distributed_table('invoices','tenant_id');
2

Configuramos RLS para aislamiento de seguridad entre tenants

ALTER TABLE orders ENABLE ROW LEVEL SECURITY; ALTER TABLE invoices ENABLE ROW LEVEL SECURITY; CREATE POLICY orders_tenant ON orders USING (tenant_id = current_setting('app.tenant_id')::INT); CREATE POLICY invoices_tenant ON invoices USING (tenant_id = current_setting('app.tenant_id')::INT); -- Ahora cada tenant solo ve sus propios datos, incluso en queries sin filtro
3

Cargamos datos de prueba: 5 tenants con 1000 pedidos cada uno y verificamos la distribución

INSERT INTO tenants VALUES (1,'Empresa A','premium'), (2,'Empresa B','basic'); INSERT INTO orders SELECT 1, generate_series(1,1000), 'Producto X', 100, '2025-01-01'::DATE + (random()*365)::INT; INSERT INTO orders SELECT 2, generate_series(1,1000), 'Producto Y', 200, '2025-01-01'::DATE + (random()*365)::INT; SELECT nodename, count(*) AS filas FROM citus_shard_sizes() GROUP BY nodename;
4

Ejecutamos consultas típicas de un SaaS multi-tenant y verificamos que son locales a un shard

SET app.tenant_id = '1'; EXPLAIN (VERBOSE) SELECT o.*, i.monto, t.plan FROM orders o JOIN invoices i USING (tenant_id, id) JOIN tenants t ON o.tenant_id = t.id WHERE o.tenant_id = 1 AND o.fecha > '2025-06-01'; -- JOIN orders-invoices: local (colocation) -- JOIN tenants: local (reference table)
5

Simulamos escalado: agregamos un worker y rebalanceamos, luego verificamos la nueva distribución

SELECT citus_add_node('worker-3', 5432); SELECT citus_rebalance_start(); SELECT citus_rebalance_status(); -- Monitorear progreso -- Ver distribución final SELECT nodename, count(*) AS shards, sum(shard_size)::numeric/1e6 AS mb FROM citus_shard_sizes() GROUP BY nodename;
