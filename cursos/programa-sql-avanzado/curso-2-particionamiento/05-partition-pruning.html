✂️ Partition Pruning

Eliminación automática de particiones irrelevantes

💡 Piénsalo así: Partition Pruning es como tener un asistente que sabe exactamente en qué cajón están las cosas. Si le pides "tráeme los informes de enero 2024", no va a revisar todos los cajones de todos los años. Va directo al cajón de enero 2024. PostgreSQL hace esto automáticamente cuando detecta que el WHERE filtra por la clave de partición.

¿Qué es Partition Pruning?

Partition Pruning es la técnica que usa PostgreSQL para eliminar particiones innecesarias durante la planificación de la consulta. Cuando el WHERE contiene condiciones sobre la columna de partición, el optimizador revisa los CHECK constraints de cada partición y descarta las que no pueden contener datos relevantes.

EXPLAIN SELECT * FROM ventas WHERE fecha = '2024-06-15'; -- Solo escanea la partición que contiene esa fecha

El pruning ocurre en tiempo de planificación (antes de ejecutar). Reduce drásticamente el I/O y la memoria necesaria. Sin pruning, una consulta escanearía todas las particiones y filtraría después.

⚠ El pruning solo funciona con la columna de partición exacta. WHERE fecha + 1 = '2024-06-15' NO activa pruning

Tipos de Filtros que Activan Pruning

El pruning se activa con: igualdad (=), IN, BETWEEN, <, >, <=, >=, IS NULL, IS NOT NULL. También funciona con condiciones compuestas con AND/OR, siempre que al menos una rama filtre por la columna de partición. Con OR, ambas ramas deben filtrar.

-- Activan pruning: WHERE fecha = '2024-06-15' WHERE fecha BETWEEN '2024-01-01' AND '2024-06-30' WHERE fecha IN ('2024-01-15', '2024-06-20') WHERE fecha >= '2024-01-01' AND region = 'ES' -- pruning por fecha

El optimizador es inteligente: si tienes fecha IN ('2024-01-15', '2025-06-20'), sabe que debe escanear 2 particiones distintas.

⚠ Las funciones y CASTs sobre la columna de partición desactivan el pruning. Usa fecha = '2024-06-15', no CAST(fecha AS text) = '2024-06-15'

Pruning Dinámico

Desde PostgreSQL 11, el pruning también puede ser dinámico: si una subconsulta o JOIN proporciona el valor de filtro en tiempo de ejecución, PostgreSQL puede aplicar pruning durante la ejecución (no solo en planificación). Esto es útil para consultas parametrizadas y prepared statements.

PREPARE q (date) AS SELECT * FROM ventas WHERE fecha = $1; EXECUTE q('2024-06-15'); -- Pruning dinámico en ejecución

El pruning dinámico permite que incluso las consultas con parámetros variables se beneficien. PostgreSQL evalúa el parámetro y decide qué particiones escanear en cada ejecución.

⚠ El pruning dinámico depende de que el planificador pueda evaluar la expresión en tiempo de ejecución

Cómo Verificar el Pruning

Usa EXPLAIN para verificar el pruning. El plan mostrará solo las particiones escaneadas. Si ves "Append" con varios child nodes, el pruning no se aplicó completamente. Si solo ves un child node, el pruning funcionó.

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM ventas WHERE fecha = '2024-06-15'; -- Ideal: "Append" con 1 child → pruning óptimo -- Malo: "Append" con 12 children → no hubo pruning

También puedes consultar pg_stats con n_dead_tup para verificar si el pruning beneficia las consultas más frecuentes.

⚠ Si ves "Subplans Removed" = 0 en EXPLAIN, el pruning no eliminó ninguna partición

Pruning con JOINs

El pruning también funciona con JOINs si la condición del JOIN incluye la columna de partición. Por ejemplo, si unes ventas con clientes y filtras por clientes.region, y region es la columna de partición, PostgreSQL puede aplicar pruning.

SELECT * FROM ventas v JOIN clientes c ON v.cliente_id = c.id WHERE c.region = 'ES'; -- Si ventas está particionada por region, pruning activo

Esto requiere que el planificador pueda propagar las condiciones del WHERE a través del JOIN. No siempre es posible, especialmente con JOINs complejos o funciones.

⚠ El pruning en JOINs depende de la calidad de las estadísticas. Estadísticas desactualizadas = pruning subóptimo

Limitaciones del Pruning

El pruning NO funciona con: (1) expresiones sobre la columna (fecha + 1), (2) funciones (UPPER(col)), (3) CASTs implícitos problemáticos, (4) condiciones con OR donde solo una rama filtra, (5) NULL comparison con IS DISTINCT FROM. Tampoco funciona con tablas sin estadísticas actualizadas.

-- NO activan pruning: WHERE CAST(fecha AS text) = '2024-06-15' -- CAST desactiva WHERE fecha + 1 = '2024-06-16' -- expresión aritmética WHERE region = 'ES' OR total > 100 -- OR sin filtro de partición

Con OR, ambas ramas deben poder podar particiones. Si solo una rama filtra por partición, la consulta escanea todo y luego filtra.

⚠ Siempre escribe las condiciones de filtro directamente sobre la columna de partición, sin funciones ni expresiones

Ejemplo paso a paso

1

Creamos una tabla particionada por rango de fecha con 12 particiones mensuales

CREATE TABLE logs (id INT, ts TIMESTAMP, nivel TEXT, mensaje TEXT) PARTITION BY RANGE (ts); -- Creamos 12 particiones, una por mes de 2024
2

Ejecutamos una consulta con filtro por fecha exacta

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM logs WHERE ts = '2024-06-15 10:30:00';
3

Verificamos en el plan que solo se escanea 1 partición (la de junio 2024). Las otras 11 son ignoradas.

Append Subplans Removed: 11 ← 11 particiones eliminadas -> Index Scan using logs_2024_06_ts_idx on logs_2024_06 ← solo 1 escaneada
4

Ahora una consulta SIN filtro de partición: se escanean todas las 12 particiones

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM logs WHERE nivel = 'ERROR'; -- Append con 12 child nodes. No hay pruning porque nivel no es columna de partición.
5

Compara el rendimiento: 1 partición escaneada (~10ms) vs 12 particiones (~120ms). El pruning puede hacer las consultas 10x más rápidas.

-- Con pruning: 8ms, 240 buffers -- Sin pruning: 95ms, 2,880 buffers -- La diferencia es proporcional al número de particiones eliminadas
