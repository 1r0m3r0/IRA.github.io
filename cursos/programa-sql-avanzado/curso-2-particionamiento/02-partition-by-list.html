📋 PARTITION BY LIST

Agrupa por valores discretos: regiones, estados, categorías

💡 Piénsalo así: PARTITION BY LIST es como clasificar tu ropa por tipo: camisas en un cajón, pantalones en otro, calcetines en otro. Cada valor (camisa, pantalón) va a su partición específica. No hay rangos, solo listas de pertenencia. Es perfecto para datos categóricos como regiones, colores o estados.

Sintaxis LIST

PARTITION BY LIST (columna) define que cada partición contiene un conjunto específico de valores. Cada partición hija se crea con FOR VALUES IN ('val1', 'val2', ...). Todos los valores de la columna deben coincidir exactamente con uno de los valores definidos en alguna partición.

CREATE TABLE pedidos (id INT, region TEXT, total NUMERIC) PARTITION BY LIST (region); CREATE TABLE pedidos_america PARTITION OF pedidos FOR VALUES IN ('US', 'CA', 'MX');

A diferencia de RANGE, LIST no tiene orden implícito. Los valores pueden estar en cualquier partición, pero cada valor solo puede estar en una partición. No puede haber solapamiento.

⚠ Si insertas un valor no cubierto por ninguna partición LIST, la BD lanza error (a menos que exista DEFAULT)

Particiones por Región

El caso de uso clásico para LIST es separar datos por región geográfica. Cada continente o país tiene su propia partición. Esto permite consultas regionales eficientes y aislamiento físico de datos de diferentes regiones.

CREATE TABLE pedidos_europa PARTITION OF pedidos FOR VALUES IN ('ES', 'FR', 'DE', 'IT'); CREATE TABLE pedidos_asia PARTITION OF pedidos FOR VALUES IN ('JP', 'CN', 'KR');

Las consultas WHERE region = 'ES' solo escanean la partición Europa, gracias al partition pruning. También facilita la gestión de datos por región (backup, archive).

⚠ La cardinalidad de la columna de partición debe ser manejable. No uses LIST con columnas de alta cardinalidad como email o nombre

LIST + DEFAULT

Combinar LIST con una partición DEFAULT es una práctica común para manejar valores nuevos o inesperados. La partición DEFAULT captura todo valor que no encaje en las particiones explícitas, actuando como red de seguridad.

CREATE TABLE pedidos_default PARTITION OF pedidos DEFAULT;

La partición DEFAULT es útil cuando el conjunto de valores puede crecer (nuevos países, nuevos productos). Pero debe monitorearse: si crece demasiado, el partition pruning no funciona con ella y las consultas se vuelven lentas.

⚠ Programa alertas cuando la partición DEFAULT supere cierto tamaño, señal de valores no clasificados

LIST vs RANGE

LIST es para categorías discretas sin orden natural; RANGE es para valores continuos con orden. LIST (región = 'US', 'MX'), RANGE (fecha > '2024'). Elegir mal puede llevar a un diseño ineficiente: LIST con alta cardinalidad crea demasiadas particiones.

-- Mal diseño: LIST en columna de alta cardinalidad CREATE TABLE usuarios (id INT, email TEXT) PARTITION BY LIST (email); -- ❌ Mala idea -- Mejor diseño: RANGE por id CREATE TABLE usuarios (id INT, email TEXT) PARTITION BY RANGE (id); -- ✅

La regla general: LIST para < 50 valores distintos; RANGE para valores continuos; HASH para distribución uniforme cuando no hay criterio natural.

⚠ No combines LIST con columnas que tengan más de ~100 valores distintos; el overhead de planificación crece

Multi-Columna LIST

PostgreSQL permite particionar por múltiples columnas. En LIST, la combinación de valores debe coincidir. Esto es útil para categorías compuestas como (región, tipo_producto) cuando necesitas granularidad fina.

CREATE TABLE ventas (region TEXT, tipo TEXT, total NUMERIC) PARTITION BY LIST (region, tipo); CREATE TABLE ventas_us_online PARTITION OF ventas FOR VALUES IN (('US', 'online'));

Las particiones multi-columna son más específicas pero más difíciles de mantener. Cada combinación única requiere su propia partición o debe caer en DEFAULT.

⚠ El número de particiones crece como producto de cardinalidades. Para region×tipo con 5 regiones y 3 tipos, necesitas hasta 15 particiones

Mantenimiento de LIST

Agregar nuevos valores a una partición LIST requiere ALTER TABLE... ATTACH PARTITION o modificar la partición existente. Si el valor existe en DEFAULT, primero debes separarlo de DEFAULT y luego agregarlo a su partición correcta.

-- Si 'BR' cayó en DEFAULT por error: CREATE TABLE pedidos_br PARTITION OF pedidos FOR VALUES IN ('BR'); -- ❌ Error, 'BR' está en DEFAULT ALTER TABLE pedidos DETACH PARTITION pedidos_default; DELETE FROM pedidos_default WHERE region != 'BR'; -- Luego ATTACH

PostgreSQL 19 simplifica este proceso con SPLIT PARTITION, que permite extraer valores de DEFAULT sin DETACH manual.

⚠ Siempre monitorea la partición DEFAULT: su existencia puede ocultar valores no clasificados que degradan el rendimiento

Ejemplo paso a paso

1

Creamos una tabla de pedidos particionada por LIST de región

CREATE TABLE pedidos (id INT, region TEXT, total NUMERIC, fecha DATE) PARTITION BY LIST (region);
2

Agregamos particiones para América, Europa y Asia-Pacífico

CREATE TABLE pedidos_america PARTITION OF pedidos FOR VALUES IN ('US', 'CA', 'MX', 'BR'); CREATE TABLE pedidos_europa PARTITION OF pedidos FOR VALUES IN ('ES', 'FR', 'DE', 'IT', 'UK'); CREATE TABLE pedidos_asia_pac PARTITION OF pedidos FOR VALUES IN ('JP', 'CN', 'KR', 'AU');
3

Insertamos algunos pedidos; PostgreSQL los enruta automáticamente

INSERT INTO pedidos VALUES (1, 'US', 150.00, '2024-01-15'); -- Va a pedidos_america INSERT INTO pedidos VALUES (2, 'ES', 200.00, '2024-02-20'); -- Va a pedidos_europa INSERT INTO pedidos VALUES (3, 'JP', 300.00, '2024-03-10'); -- Va a pedidos_asia_pac
4

Consultamos solo pedidos de Europa; partition pruning limita el escaneo a una partición

EXPLAIN SELECT * FROM pedidos WHERE region = 'ES'; -- Solo escanea pedidos_europa, ignora las demás particiones
5

Si insertamos un valor no cubierto (ej: 'IN' para India), PostgreSQL lanza error. Para evitarlo, creamos una partición DEFAULT que capture valores no clasificados

CREATE TABLE pedidos_default PARTITION OF pedidos DEFAULT; INSERT INTO pedidos VALUES (4, 'IN', 250.00, '2024-04-01'); -- Ahora va a pedidos_default

Resumen del módulo

  • PARTITION BY LIST agrupa datos por valores discretos usando FOR VALUES IN (...)
  • Ideal para datos categóricos con cardinalidad baja: regiones, estados, colores
  • No uses LIST con alta cardinalidad (>100 valores); prefiere RANGE o HASH
  • La partición DEFAULT captura valores no clasificados; monitórealas para evitar degradación
  • PostgreSQL 19 permite extraer valores de DEFAULT con SPLIT PARTITION
  • El partition pruning funciona con LIST cuando el WHERE usa igualdad exacta
