🔑 Shard Key Design

Diseña la clave de sharding perfecta

💡 Piénsalo así: Elegir la shard key es como elegir el código postal para repartir correo. Si usas el código postal correcto, cada cartero reparte solo en su zona. Si usas uno malo, un cartero termina recorriendo toda la ciudad (hotspot) mientras otros están ociosos. La shard key determina TODO: rendimiento, escalabilidad y mantenibilidad.

Cardinalidad y Uniformidad

Una buena shard key debe tener alta cardinalidad (muchos valores distintos) y distribución uniforme (cada valor tiene aproximadamente la misma cantidad de datos). Ejemplos buenos: tenant_id (1000 tenants con datos similares), user_id, order_id. Ejemplos malos: país (si 80% está en US), género (solo 2 valores).

-- Evaluar cardinalidad de posibles shard keys SELECT count(DISTINCT tenant_id) AS cardinalidad FROM orders; -- Evaluar uniformidad (distribución) SELECT tenant_id, count(*) FROM orders GROUP BY tenant_id ORDER BY count(*) DESC LIMIT 5; -- Si un tenant tiene 80% de los datos, es mala shard key

La cardinalidad ideal es al menos 10× el número de shards planeados. Si tienes 8 shards, necesitas al menos 80 valores distintos. Menos que eso causa distribución desigual.

⚠ La uniformidad puede cambiar con el tiempo. Un tenant que hoy es pequeño puede crecer y convertirse en hotspot. Monitorea continuamente.

Query Locality

La locality mide qué porcentaje de consultas pueden resolverse con un solo shard. Idealmente, todas las consultas incluyen la shard key en el WHERE, permitiendo que Vitess/Citus enrute al shard exacto. Las consultas sin shard key requieren scatter (enviar a todos los shards).

-- Buena locality: la consulta incluye tenant_id SELECT * FROM orders WHERE tenant_id = 101 AND fecha > '2024-01-01'; -- Va a un solo shard ✅ -- Mala locality: sin shard key SELECT * FROM orders WHERE total > 1000; -- Scatter a todos los shards ❌

Cada consulta scatter multiplica la carga: si tienes 16 shards, cada scatter consume 16× más recursos. Diseña tu shard key para que la mayoría de consultas incluyan la clave.

⚠ Las consultas de reporting sin shard key son inevitables. Usa una réplica de solo-lectura (sin sharding) para reporting.

Hash vs Range

Hash partitioning distribuye datos uniformemente pero no soporta range scans eficientes. Range partitioning permite scans por rango pero causa hotspots en el rango actual (time-series). La elección depende del patrón de acceso: hash para OLTP, range para analítica por períodos.

-- Hash: datos uniformes, no importa el valor SELECT citus_create_distributed_table('orders','tenant_id'); -- Range: datos ordenados, útiles para time-series CREATE TABLE logs PARTITION BY RANGE (ts);

Para sistemas OLTP con acceso por tenant, hash es la mejor opción. Para time-series con consultas por rango temporal, usa range partitioning con rotación automática de particiones.

⚠ Con hash partitioning, las consultas por rango pueden necesitar scatter. Si tu app principal consulta por rango de fechas, considera shard key compuesta.

Shard Key Compuesta

Una shard key compuesta usa dos o más columnas. Citus y Vitess soportan shard keys de múltiples columnas con ciertas limitaciones. Ejemplo: (tenant_id, fecha) permite buena distribución y range scans dentro de un tenant. La primera columna determina la distribución principal.

CREATE TABLE orders ( tenant_id INT, order_date DATE, data JSONB ) PARTITION BY RANGE (tenant_id, order_date); -- Consultas que incluyen tenant_id van a un shard -- Dentro del shard, las filas están ordenadas por order_date

La shard key compuesta es un tradeoff: mejora locality para un subconjunto de consultas pero puede complicar el rebalanceo. Úsala solo cuando una columna simple no cubre el patrón de acceso.

⚠ No todas las plataformas de sharding soportan keys compuestas. Verifica la documentación de Citus, Vitess o tu solución elegida.

Anti-patrones Comunes

Errores frecuentes al elegir shard key: secuencias auto-incrementales (todas las inserciones van al mismo shard), fechas sin combinar (hotspot en el día actual), columnas con pocos valores (solo 2-3 valores distintos), y UUIDs random (distribución perfecta pero sin locality).

-- Anti-patrón: shard key = id secuencial -- Todas las inserciones caen en el mismo shard ❌ -- Anti-patrón: shard key = fecha actual -- Hotspot en la partición del día ❌ -- Patrón correcto: shard key = tenant_id + fecha (compuesta) -- Buen balance + range scan ✅

Si usas UUID como shard key, la distribución es perfecta pero pierdes locality porque las consultas rara vez filtran por UUID. Siempre prioriza la locality sobre la distribución perfecta.

⚠ El peor anti-patrón es cambiar la shard key después del despliegue. Elegir bien la primera vez ahorra meses de resharding.

Patrón Multi-Tenant

En sistemas SaaS multi-tenant, tenant_id es la mejor shard key. Garantiza: (1) distribución uniforme si los tenants tienen similar volumen, (2) locality perfecta (todas las consultas incluyen tenant_id), (3) colocation con tablas relacionadas (invoices, logs).

-- Esquema multi-tenant óptimo SELECT citus_create_distributed_table('tenants','id'); -- reference table SELECT citus_create_distributed_table('orders','tenant_id'); SELECT citus_create_distributed_table('invoices','tenant_id'); -- JOINs entre orders e invoices son locales (colocation) -- JOIN con tenants es local (reference table)

El patrón multi-tenant con reference table para la tabla de tenants y tablas distribuidas para datos por tenant es la arquitectura más exitosa en producción SaaS.

⚠ Si un tenant crece desproporcionadamente (>20% del total), considera un "tenant VIP" con su propio shard dedicado.

Ejemplo paso a paso

1

Analizamos la distribución de datos actual para identificar la mejor shard key para un sistema SaaS con 500 empresas

-- Ver distribución por tenant SELECT tenant_id, count(*) AS filas, pg_size_pretty(sum(pg_column_size(data))) AS total_bytes FROM orders GROUP BY tenant_id ORDER BY filas DESC LIMIT 10;
2

Evaluamos tres candidatos: tenant_id (alta cardinalidad), created_at (sesgo temporal), country (sesgo geográfico)

SELECT 'tenant_id' AS key, count(DISTINCT tenant_id) AS cardinalidad FROM orders UNION ALL SELECT 'created_at', count(DISTINCT date_trunc('month', created_at)) FROM orders UNION ALL SELECT 'country', count(DISTINCT country) FROM orders;
3

Simulamos cómo se distribuirían los datos con hash partitioning en 8 shards

-- Simulación: asignar shard con hash de tenant_id SELECT abs(hashint4(tenant_id) % 8) AS shard, count(*) FROM orders GROUP BY shard ORDER BY shard; -- Ideal: cada shard tiene ~12.5% de los datos -- Si algún shard tiene >20%, hay skew
4

Diseñamos la shard key final: tenant_id para distribución + range partitioning por fecha dentro de cada shard

-- Tabla multi-tenant con sharding por hash y particionamiento por rango CREATE TABLE orders ( tenant_id INT NOT NULL, order_date DATE NOT NULL, ... ) PARTITION BY RANGE (order_date); -- Distribuir por hash en Citus SELECT citus_create_distributed_table('orders','tenant_id'); -- Particionar por fecha dentro de cada shard CREATE TABLE orders_2025_q1 PARTITION OF orders FOR VALUES FROM ('2025-01-01') TO ('2025-04-01');
5

Verificamos la colocation con tablas relacionadas y probamos queries antes del despliegue

-- Verificar colocation SELECT logicalrelid, colocationid FROM pg_dist_partition WHERE logicalrelid IN ('orders'::regclass, 'invoices'::regclass); -- Mismo colocationid = JOINs locales ✅ -- Query de prueba: debe ir a un solo shard EXPLAIN (VERBOSE) SELECT * FROM orders JOIN invoices USING (tenant_id) WHERE tenant_id = 101 AND order_date > '2025-01-01';

Resumen del módulo

  • Una buena shard key tiene alta cardinalidad, distribución uniforme y buena query locality
  • Hash partitioning distribuye uniformemente; range partitioning favorece scans por rango
  • tenant_id es la mejor shard key para sistemas multi-tenant SaaS
  • Las consultas sin shard key requieren scatter (enviar a todos los shards) y consumen más recursos
  • La colocation permite JOINs locales entre tablas con la misma shard key
  • Anti-patrones: secuencias auto-incrementales, fechas sin combinar, columnas con baja cardinalidad
