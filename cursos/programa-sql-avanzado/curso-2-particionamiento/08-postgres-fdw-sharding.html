🌐 postgres_fdw Sharding

Sharding nativo con Foreign Data Wrappers

💡 Piénsalo así: postgres_fdw es como tener una mensajería entre servidores. Le dices a PostgreSQL "oye, esa tabla que necesitas está en otro servidor, pero quiero consultarla como si estuviera aquí". PostgreSQL crea un "enlace" (foreign server) y mapea usuarios, tablas y esquemas. Es la forma más nativa de sharding en PostgreSQL.

Instalación y Extensión

postgres_fdw viene incluido en PostgreSQL pero debe activarse con CREATE EXTENSION. Es un wrapper estándar que usa libpq internamente para conectarse al servidor remoto. Soporta autenticación por contraseña, certificados SSL y conexiones con keepalive.

CREATE EXTENSION postgres_fdw; CREATE SERVER shard_us FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host 'shard1.example.com', port '5432', dbname 'orders_us'); CREATE USER MAPPING FOR current_user SERVER shard_us OPTIONS (user 'fdw_user', password 'secret');

El SERVER guarda la dirección del host remoto. El USER MAPPING asocia el usuario local con credenciales del remoto. Nunca expongas contraseñas en código: usa variables de entorno o archivos .pgpass.

⚠ Las contraseñas se almacenan en texto plano en pg_user_mappings. Protege el acceso a la BD.

Creación de Foreign Tables

Hay dos formas de crear tablas foreign: manual (CREATE FOREIGN TABLE) o automática (IMPORT FOREIGN SCHEMA). IMPORT FOREIGN SCHEMA trae todas las tablas de un esquema remoto. Cada tabla foreign aparece como una tabla local pero los datos residen en el remoto.

-- Manual: estructura específica CREATE FOREIGN TABLE orders_remote ( id BIGINT, cliente_id INT, total NUMERIC, fecha DATE ) SERVER shard_us OPTIONS (schema_name 'public', table_name 'orders'); -- Automático: importa todo un esquema IMPORT FOREIGN SCHEMA public FROM SERVER shard_us INTO public;

IMPORT FOREIGN SCHEMA respeta los tipos de datos y constraints básicos del remoto. No importa índices, triggers o defaults.

⚠ Las foreign tables no soportan TRUNCATE. Usa DELETE sin WHERE o crea una función en el remoto.

Query Pushdown

El pushdown es la capacidad de enviar filtros (WHERE), joins y agregaciones al servidor remoto. PostgreSQL analiza la consulta y decide qué partes puede delegar. El pushdown reduce drásticamente la cantidad de datos transferidos porque el remoto filtra antes de enviar.

-- PostgreSQL envía este WHERE al remoto EXPLAIN (VERBOSE) SELECT count(*), region FROM orders_remote WHERE fecha >= '2024-01-01' GROUP BY region; -- Output: "Foreign Scan" con "Remote SQL: SELECT count(*), region FROM public.orders WHERE (fecha >= '2024-01-01') GROUP BY region"

No todos los operadores hacen pushdown. Funciones custom, tipos no estándar y ciertas cláusulas pueden ejecutarse localmente. Siempre verifica con EXPLAIN (VERBOSE) qué se envía al remoto.

⚠ Los JOINs entre tablas foreign de distintos servidores NO hacen pushdown. Se traen los datos y se ejecutan localmente.

FDW + Partitioning = Sharding Nativo

La combinación más potente: crea una tabla particionada local y asigna cada partición a un servidor remoto diferente usando FDW. Esto te da sharding geográfico: los datos de US van a shard_us, los de EU a shard_eu, etc. Totalmente transparente para las consultas.

CREATE TABLE orders (id BIGINT, region TEXT, ...) PARTITION BY LIST (region); CREATE FOREIGN TABLE orders_us PARTITION OF orders FOR VALUES IN ('US') SERVER shard_us OPTIONS (schema_name 'public', table_name 'orders_us'); CREATE FOREIGN TABLE orders_eu PARTITION OF orders FOR VALUES IN ('EU') SERVER shard_eu OPTIONS (schema_name 'public', table_name 'orders_eu');

Las consultas SELECT * FROM orders WHERE region='US' solo tocan shard_us. PostgreSQL usa partition pruning incluso con foreign tables.

⚠ Los INSERTs a la tabla padre requieren que PostgreSQL pueda determinar la partición de destino. Sin partition key en el INSERT, fallará.

Rendimiento y Conexiones

postgres_fdw abre una conexión por sesión por servidor foreign. Si tienes 100 conexiones locales y 3 servidores remotos, puedes tener hasta 300 conexiones abiertas. Usa pooling (PgBouncer) en los servidores remotos para manejarlo.

-- Configurar batch_size para INSERTs masivos ALTER SERVER shard_us OPTIONS (ADD batch_size '1000'); -- Los INSERTs se agrupan en lotes de 1000 filas -- Reducir fetch_size si las consultas devuelven pocas filas ALTER SERVER shard_us OPTIONS (ADD fetch_size '50');

Las opciones batch_size y fetch_size controlan el rendimiento de red. batch_size agrupa INSERTs en una sola transacción remota. fetch_size controla cuántas filas trae cada viaje de red.

⚠ Las transacciones distribuidas (2PC) no son automáticas. Si un shard falla, el COMMIT queda inconsistente. Usa tablas locales para transacciones críticas.

Limitaciones y Alternativas

postgres_fdw no soporta escrituras concurrentes distribuidas (no hay 2PC nativo), no balancea carga automáticamente, y los JOINs cross-shard son lentos. Para cargas OLTP pesadas, considera Citus o Vitess. Para datos históricos o read-heavy, FDW es perfecto.

-- FDW: ideal para data warehouse distribuido -- Citus: ideal para OLTP multi-tenant -- Vitess: ideal para MySQL-compatible a hiperescala -- Elige según tu patrón de acceso

FDW brilla en: integración de sistemas legacy, data lakes distribuidos, migración gradual (shawshank pattern) donde reads van al nuevo sistema y writes al viejo.

⚠ No uses FDW para tablas con altísima concurrencia de escritura (>1000 writes/segundo). La latencia de red y la falta de 2PC causarán problemas.

Ejemplo paso a paso

1

Instalamos la extensión y creamos el servidor foreign que apunta a nuestro shard en AWS

CREATE EXTENSION postgres_fdw; CREATE SERVER shard_aws FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host 'db-shard1.aws.com', port '5432', dbname 'ventas_2025');
2

Creamos el mapeo de usuario local al remoto y verificamos la conexión con una consulta simple

CREATE USER MAPPING FOR CURRENT_USER SERVER shard_aws OPTIONS (user 'fdw_user', password 'ClaveSegura2025'); -- Verificar conectividad SELECT * FROM dblink('shard_aws', 'SELECT version()') AS v(texto text);
3

Importamos las tablas del esquema remoto para que aparezcan como locales

IMPORT FOREIGN SCHEMA public LIMIT TO (clientes, ordenes, productos) FROM SERVER shard_aws INTO public_sync; -- Ahora podemos consultar clientes, ordenes y productos como si fueran tablas locales
4

Creamos una tabla particionada local que distribuye datos entre shard AWS y shard on-premise

CREATE TABLE ventas (id BIGSERIAL, region TEXT, total DECIMAL, fecha DATE) PARTITION BY LIST (region); CREATE FOREIGN TABLE ventas_aws PARTITION OF ventas FOR VALUES IN ('US','CA','MX') SERVER shard_aws OPTIONS (schema_name 'public', table_name 'ventas'); CREATE FOREIGN TABLE ventas_onprem PARTITION OF ventas FOR VALUES IN ('EU','APAC') SERVER shard_onprem OPTIONS (schema_name 'public', table_name 'ventas');
5

Ejecutamos una consulta cross-shard y verificamos el pushdown con EXPLAIN

EXPLAIN (VERBOSE) SELECT region, count(*) FROM ventas WHERE fecha > '2025-01-01' GROUP BY region; -- Cada shard ejecuta su parte del GROUP BY localmente -- El coordinador solo suma los resultados parciales

Resumen del módulo

  • postgres_fdw permite acceder a datos remotos como si fueran tablas locales

  • Query pushdown envía filtros, GROUP BY y JOINs al servidor remoto para reducir datos transferidos

  • batch_size y fetch_size optimizan el rendimiento de red para INSERTs y SELECTs
  • FDW no soporta 2PC: las transacciones distribuidas no son atómicas entre shards
