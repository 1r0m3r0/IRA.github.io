🔀 MERGE / SPLIT (PG 19)

Fusiona y divide particiones en caliente

💡 Piénsalo así: MERGE y SPLIT son como remodelar los cuartos de tu casa. SPLIT divide un cuarto grande en dos más pequeños (una partición grande se parte en dos rangos). MERGE une dos cuartos pequeños en uno más grande. En PostgreSQL 19, esto se hace SIN apagar la casa (sin downtime).

  • Aplicar la sintaxis correcta con ejemplos prácticos de consultas
  • Evitar errores comunes y optimizar el rendimiento
  • Desarrollar intuición para elegir la técnica adecuada

¿Qué aprenderás?

  • Cómo SPLIT divide una partición grande en dos subrangos más pequeños
  • Cómo MERGE fusiona dos particiones adyacentes en una sola

  • Cuándo SPLIT es mejor que re-particionar desde cero
  • Estrategias de mantenimiento proactivo de particiones con estas herramientas

SPLIT Básico

SPLIT PARTITION divide una partición existente en dos o más sub-particiones. Los datos se redistribuyen automáticamente según los nuevos rangos. PostgreSQL 19 reescribe solo metadatos, no los datos físicos, lo que hace SPLIT prácticamente instantáneo independientemente del tamaño de la partición.

ALTER TABLE orders SPLIT PARTITION orders_2023 INTO ( PARTITION orders_2023_q1 VALUES FROM ('2023-01-01') TO ('2023-07-01'), PARTITION orders_2023_q2 VALUES FROM ('2023-07-01') TO ('2024-01-01') );

Los nuevos nombres y rangos son totalmente configurables. La operación adquiere un breve bloqueo exclusivo para intercambiar metadatos, pero no mueve ninguna fila.

⚠ SPLIT no funciona si la partición tiene dependencias como foreign keys. Debes eliminarlas temporalmente.

SPLIT en Múltiples Sub-particiones

Puedes SPLIT una partición en más de dos subrangos a la vez. Esto es útil cuando una partición mensual resulta demasiado grande y quieres dividirla en semanal o diario. La sintaxis acepta cualquier número de PARTITION clauses.

ALTER TABLE logs SPLIT PARTITION logs_2025 INTO ( PARTITION logs_2025_q1 VALUES FROM ('2025-01-01') TO ('2025-04-01'), PARTITION logs_2025_q2 VALUES FROM ('2025-04-01') TO ('2025-07-01'), PARTITION logs_2025_q3 VALUES FROM ('2025-07-01') TO ('2025-10-01'), PARTITION logs_2025_q4 VALUES FROM ('2025-10-01') TO ('2026-01-01') );

Cada sub-partición recibe los datos que le corresponden según su rango. Si alguna fila no cae en ningún rango, SPLIT falla con un error de validación.

⚠ Asegúrate de que los rangos cubran exactamente el rango original. Cualquier hueco causará un error.

MERGE Básico

MERGE PARTITIONS fusiona dos o más particiones adyacentes en una sola. Las particiones deben ser consecutivas en el rango. PostgreSQL consolida los metadatos y los datos quedan accesibles desde la nueva partición única.

ALTER TABLE orders MERGE PARTITIONS (orders_2023_q1, orders_2023_q2) INTO PARTITION orders_2023;

MERGE es el inverso exacto de SPLIT. Después del MERGE, la nueva partición contiene todos los datos de las originales. Las particiones originales dejan de existir como entidades separadas.

⚠ MERGE solo funciona en particiones adyacentes. No puedes fusionar enero y marzo saltándose febrero.

MERGE con Validación

PostgreSQL 19 valida que las particiones a fusionar sean estrictamente adyacentes y que no haya solapamiento con otras particiones existentes. También verifica que las tablas subyacentes tengan la misma estructura y constraints.

-- Verificar adyacencia antes de MERGE SELECT range '[' || range_from || ',' || range_to || ')' FROM pg_partition_tree('orders_2023_q1'); -- Debe terminar exactamente donde empieza orders_2023_q2

Si las particiones no son adyacentes o hay un hueco, PostgreSQL lanza un error claro indicando el problema de rango. No se puede forzar un MERGE no adyacente.

⚠ Si necesitas fusionar rangos no adyacentes, primero SPLIT la partición del medio para crear un rango contiguo.

SPLIT vs DETACH+ATTACH

Antes de PG 19, dividir una partición requería: (1) DETACH la partición grande, (2) crear nuevas tablas particionadas, (3) INSERT de datos, (4) ATTACH las nuevas particiones. SPLIT hace TODO esto en un solo comando atómico, sin mover datos y sin ventana de inconsistencia.

-- Antes de PG 19 (5 comandos, horas de migración): ALTER TABLE orders DETACH PARTITION orders_2023; CREATE TABLE orders_2023_q1 (...); INSERT INTO orders_2023_q1 SELECT * FROM orders_2023 WHERE fecha < '2023-07-01'; ALTER TABLE orders ATTACH PARTITION orders_2023_q1 FOR VALUES FROM ('2023-01-01') TO ('2023-07-01'); DROP TABLE orders_2023;

Con SPLIT, el mismo resultado se logra con un comando que toma milisegundos. Los metadatos se reescriben atómicamente.

⚠ SPLIT no elimina la tabla original inmediatamente; la reasigna como nuevo contenedor de metadatos.

Estrategia de Mantenimiento Proactivo

Usa SPLIT y MERGE como parte de tu rutina de mantenimiento. Monitorea el tamaño de particiones semanalmente. Si una partición supera el umbral (ej. 100 GB), haz SPLIT. Si varias particiones están por debajo del mínimo (ej. 1 GB), haz MERGE.

-- Monitoreo semanal: encontrar particiones candidatas a SPLIT SELECT schemaname,tablename,pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) FROM pg_tables WHERE tablename LIKE 'orders_%' AND pg_total_relation_size(schemaname||'.'||tablename) > 100e9;

Automatiza con pg_cron: un job que ejecuta SPLIT en particiones que superan el umbral y MERGE en las que están infrautilizadas.

⚠ Programa SPLIT/MERGE en horas de baja actividad. Aunque son rápidos, el ACCESS EXCLUSIVE LOCK puede afectar consultas concurrentes.

Ejemplo paso a paso

1

Creamos una tabla particionada por trimestres para empezar organizados

CREATE TABLE pedidos (id BIGSERIAL, fecha DATE, total DECIMAL, cliente_id INT) PARTITION BY RANGE (fecha); CREATE TABLE pedidos_2025_q1 PARTITION OF pedidos FOR VALUES FROM ('2025-01-01') TO ('2025-04-01'); CREATE TABLE pedidos_2025_q2 PARTITION OF pedidos FOR VALUES FROM ('2025-04-01') TO ('2025-07-01'); CREATE TABLE pedidos_2025_q3 PARTITION OF pedidos FOR VALUES FROM ('2025-07-01') TO ('2025-10-01'); CREATE TABLE pedidos_2025_q4 PARTITION OF pedidos FOR VALUES FROM ('2025-10-01') TO ('2026-01-01');
2

El Q1 de 2025 creció tanto (80 GB) que necesitamos dividirlo en meses con SPLIT

ALTER TABLE pedidos SPLIT PARTITION pedidos_2025_q1 INTO ( PARTITION pedidos_2025_01 VALUES FROM ('2025-01-01') TO ('2025-02-01'), PARTITION pedidos_2025_02 VALUES FROM ('2025-02-01') TO ('2025-03-01'), PARTITION pedidos_2025_03 VALUES FROM ('2025-03-01') TO ('2025-04-01') );
3

Verificamos que el SPLIT funcionó consultando el árbol de particiones

SELECT inhrelid::regclass FROM pg_inherits WHERE inhparent = 'pedidos'::regclass; -- Resultado: pedidos_2025_01, pedidos_2025_02, pedidos_2025_03, -- pedidos_2025_q2, pedidos_2025_q3, pedidos_2025_q4
4

Los trimestres Q3 y Q4 están pequeños (< 5 GB cada uno). Los fusionamos con MERGE para reducir overhead de metadatos

ALTER TABLE pedidos MERGE PARTITIONS (pedidos_2025_q3, pedidos_2025_q4) INTO PARTITION pedidos_2025_s2;
5

Verificamos la estructura final y ejecutamos ANALYZE para actualizar estadísticas

SELECT inhrelid::regclass FROM pg_inherits WHERE inhparent = 'pedidos'::regclass; -- Resultado: pedidos_2025_01, pedidos_2025_02, pedidos_2025_03, -- pedidos_2025_q2, pedidos_2025_s2 ANALYZE pedidos;

Resumen del módulo

  • SPLIT divide una partición grande en subrangos sin mover datos físicos (solo metadatos)

  • SPLIT/MERGE reemplazan el proceso manual de DETACH+ATTACH con un solo comando atómico
  • Las particiones a MERGE deben ser estrictamente adyacentes en el rango
  • Monitorea tamaños de particiones y usa SPLIT/MERGE para mantener el equilibrio
  • SPLIT acepta múltiples sub-particiones en un solo comando
