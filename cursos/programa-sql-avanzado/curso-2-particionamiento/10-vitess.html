⚡ Vitess

Sharding a escala planetaria (MySQL-compatible)

💡 Piénsalo así: Vitess es como el sistema de enrutamiento de Amazon. No sabes en qué almacén está tu paquete, pero el sistema de enrutamiento lo sabe. Vitess usa un VSchema (esquema virtual) que mapea tablas a shards. Tú consultas como si fuera una sola base de datos, y Vitess enruta la consulta al shard correcto.

Componentes de Vitess

Vitess tiene tres componentes principales: VTGate (proxy de enrutamiento que recibe consultas SQL y las dirige), VTTablet (proceso que maneja cada shard MySQL), y Topology Service (etcd/Consul que guarda la configuración del cluster). VTGate es el entry point para todas las aplicaciones.

# Arquitectura típica Vitess # App → VTGate (proxy) → VTTablet (shard 1) → MySQL # → VTTablet (shard 2) → MySQL # → VTTablet (shard N) → MySQL # Topology Service (etcd) coordina todo

VTGate implementa MySQL wire protocol, por lo que cualquier cliente MySQL puede conectarse. No requiere drivers especiales. VTGate también maneja pooling de conexiones y timeout.

⚠ VTGate es el cuello de botella potencial. En clusters grandes (>100 shards), escala horizontalmente con múltiples VTGate detrás de un balanceador.

VSchema: El Esquema Virtual

El VSchema es el corazón de Vitess. Define cómo las tablas se mapean a shards. Puedes tener tablas distribuídas (por shard key), reference tables (replicadas en todos los shards) y tablespace-like mappings. Vitess usa el VSchema para decidir a qué shard enrutar cada consulta.

{ "sharded": true, "vindexes": { "tenant_hash": {"type": "hash"} }, "tables": { "orders": { "column_vindexes": [{"column": "tenant_id", "name": "tenant_hash"}] } } }

El VSchema soporta múltiples tipos de vindex (índices virtuales): hash, lookup, uniq, region_experimental. Cada vindex define cómo se mapea el valor de la columna al shard correspondiente.

⚠ Cambiar el VSchema en producción requiere planificación. Vitess hace "resharding" para redistribuir datos cuando cambia el esquema.

Vitess vs Citus

La diferencia fundamental: Vitess funciona con MySQL (y experimentalmente con PostgreSQL), mientras Citus es una extensión de PostgreSQL. Vitess nació en YouTube para escalar MySQL. Citus nació como extensión de PostgreSQL. Vitess opera como proxy externo; Citus como extensión interna.

Vitess: YouTube (MySQL) → 1000+ shards → VTGate → App Citus: PostgreSQL → EXTENSION → coordinator/worker → App

Vitess maneja mejor cargas de alta escritura gracias al MySQL binlog para replicación. Citus maneja mejor consultas analíticas complejas gracias al optimizador PostgreSQL. La elección depende del stack actual de la organización.

⚠ Vitess no soporta todas las features de MySQL (trigger, stored procedures, ciertos DDL). Verifica compatibilidad antes de migrar.

Resharding: Merge/Split Automático

Cuando un shard crece demasiado, Vitess permite "splitting" automático: parte los datos en dos shards más pequeños. El proceso no requiere downtime: Vitess crea los nuevos shards, replica datos incrementalmente, y cambia el routing cuando la sincronización se completa.

# Comando de resharding (vtctlclient) vtctlclient Reshard customer.keyspace.workflow \ 'customer/80-', 'customer/-80'

El resharding en Vitess es transparente para la aplicación. Durante la migración, VTGate escribe en ambos conjuntos de shards (old y new). Cuando los nuevos shards están al día, el tráfico se redirige instantáneamente.

⚠ El resharding consume recursos significativos. Monitorea la réplica lag durante el proceso para no saturar los shards.

Keyspaces y Sharding

Un keyspace en Vitess equivale a una base de datos lógica. Un keyspace puede ser sharded (particionado) o unsharded (una sola BD). Cada keyspace puede tener su propio esquema de sharding. Los keyspaces permiten aislar tenants o dominios dentro del mismo cluster.

-- Crear keyspace vtctlclient CreateKeyspace -sharding_column_name=tenant_id users -- Crear tabla en keyspace sharded CREATE TABLE users (id BIGINT, tenant_id INT, name TEXT) VITESS_SHARD_BY tenant_id;

Los keyspaces facilitan la migración gradual: puedes tener un keyspace sharded y otro unsharded, y mover tablas entre ellos progresivamente.

⚠ Cada keyspace requiere su propio conjunto de shards. No compartas un shard entre múltiples keyspaces.

Casos de Uso Reales

YouTube usa Vitess desde 2011 para escalar su metadata de videos. Slack migró su infraestructura MySQL a Vitess. Pinterest usa Vitess para tableros y pines. Square, HubSpot y JD.com también lo usan. Vitess maneja petabytes de datos y millones de consultas por segundo.

YouTube: ~1,000+ shards, petabytes de metadata Slack: ~150 shards, millones de mensajes/día Pinterest: ~300 shards, billones de pines

Vitess es uno de los pocos proyectos de sharding que ha probado su resiliencia en producción a escala planetaria. Es graduado de CNCF (Cloud Native Computing Foundation).

⚠ Vitess tiene una curva de aprendizaje empinada. La configuración inicial (topology, keyspaces, VSchema) requiere experiencia en MySQL y administración de clusters.

Ejemplo paso a paso

1

Desplegamos un cluster Vitess mínimo con un keyspace y dos shards usando etcd como topology service

# Inicializar topology service (etcd) etcd --listen-client-urls http://localhost:2379 --advertise-client-urls http://localhost:2379 & vtctlclient -server localhost:15999 InitShardMaster -force customer/0 master1:15000
2

Creamos el keyspace "ventas" con sharding por tenant_id y configuramos el VSchema

vtctlclient CreateKeyspace -sharding_column_name=tenant_id ventas # VSchema JSON con vindex hash vtctlclient ApplyVSchema -vschema '{ "sharded": true, "vindexes": {"hash": {"type": "hash"}}, "tables": {"pedidos": {"column_vindexes": [{"column": "tenant_id", "name": "hash"}]}} }' ventas
3

Nos conectamos a VTGate (como si fuera MySQL) y creamos la tabla distribuida

mysql -h 127.0.0.1 -P 15306 -u root CREATE TABLE pedidos ( id BIGINT AUTO_INCREMENT, tenant_id INT NOT NULL, cliente VARCHAR(100), total DECIMAL(10,2), PRIMARY KEY (id) ); -- Vitess automáticamente distribuye los datos según tenant_id
4

Insertamos datos y verificamos la distribución entre shards

INSERT INTO pedidos (tenant_id, cliente, total) VALUES (101, 'Cliente A', 150.00), (202, 'Cliente B', 250.00), (303, 'Cliente C', 350.00); -- Ver en qué shards cayeron SELECT shard, count(*) FROM pedidos GROUP BY shard;
5

Escalamos: agregamos un tercer shard y hacemos resharding para redistribuir datos

vtctlclient Reshard ventas.reshard_workflow \ 'ventas/-40', 'ventas/40-80', 'ventas/80-' -- VTGate cambia el routing automáticamente cuando el resharding completa

Componentes de Vitess

VTGate

Proxy de enrutamiento. Recibe consultas SQL y las dirige al VTablet correcto.

VTTablet

Proceso por shard. Maneja la conexión a MySQL y las operaciones de replicación.

Topology

Etcd/Consul. Guarda la configuración del cluster, shards y tablets.
