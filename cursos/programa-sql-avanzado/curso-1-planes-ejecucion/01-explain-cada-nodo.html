🔍 EXPLAIN Cada Nodo

Descifra el plan de ejecución nodo por nodo

💡 Piénsalo así: EXPLAIN ANALYZE es como los frenos de un auto de carreras. No quieres ver los frenos en la recta principal, pero cuando llegas a la curva, quieres saber exactamente cómo funcionan. Cada nodo del plan de ejecución es una pieza del motor de tu consulta: sábelo entender y sabrás dónde está perdiendo potencia.

🎯 ¿Qué aprenderás?

  • Comprender el concepto fundamental de SQL explicado en este módulo
  • Aplicar la sintaxis correcta con ejemplos prácticos de consultas
  • Evitar errores comunes y optimizar el rendimiento
  • Desarrollar intuición para elegir la técnica adecuada

¿Qué aprenderás?

  • A leer cada nodo del plan EXPLAIN: Seq Scan, Index Scan, Bitmap Heap Scan, Merge Join
  • A diferenciar costos startup vs total y sus implicaciones
  • A identificar cuellos de botella por el tipo de nodo dominante
  • A elegir el mejor nodo según el tamaño de tabla y filtros
  • A diagnosticar por qué una consulta es lenta con solo ver el plan

Seq Scan

Escaneo secuencial: lee toda la tabla bloque por bloque desde el primero hasta el último. Es el método más simple y a menudo el más eficiente para tablas pequeñas o cuando necesitas recuperar más del 30% de las filas.

EXPLAIN SELECT * FROM usuarios;

PostgreSQL estima el costo como seq_page_cost × páginas + cpu_tuple_cost × filas. No requiere índice porque no puede saltarse bloques.

⚠ No uses Seq Scan en tablas grandes con filtros selectivos (>30% filas ok, <1% mal)

Index Scan

Escaneo por índice: navega el árbol B+ del índice para encontrar las direcciones exactas de las filas que cumplen la condición. Ideal para búsquedas puntuales con alta selectividad.

EXPLAIN SELECT * FROM usuarios WHERE id = 42;

El costo incluye la navegación del índice (altura del árbol, típicamente 3-4 niveles) más el acceso aleatorio a las páginas del heap. Muy eficiente cuando recuperas pocas filas.

⚠ Si SELECT * pide muchas columnas, cada fila requiere un acceso aleatorio al heap

Bitmap Heap Scan

Combina múltiples índices: construye un bitmap en memoria con las ubicaciones de las filas candidatas y luego lee los bloques físicos en orden. Balance perfecto entre selectividad y acceso secuencial.

EXPLAIN SELECT * FROM ventas WHERE fecha > '2024-01-01' AND monto > 1000;

Primero crea un bitmap con los bloques que contienen filas válidas (Bitmap Index Scan), luego escanea el heap en orden físico. Reduce los accesos aleatorios comparado con Index Scan.

⚠ Si el bitmap es muy grande, PostgreSQL puede preferir Seq Scan directamente

Merge Join

Junta dos conjuntos ordenados escaneando ambos simultáneamente como una cremallera. Requiere que los datos de entrada estén ordenados por la clave de join.

EXPLAIN SELECT * FROM a JOIN b ON a.id = b.id ORDER BY a.id;

Cada tabla se ordena (si no lo está ya por un índice) y luego se fusiona. El costo total es O(N+M), pero si las tablas no están ordenadas, el sort adicional puede hacerlo más caro que Hash Join.

⚠ Si los datos no están pre-ordenados, el Sort externo puede ser prohibitivo

Nested Loop

Bucle anidado: para cada fila de la tabla externa, busca las filas correspondientes en la tabla interna usando un índice. Ideal cuando una tabla es muy pequeña.

EXPLAIN SELECT * FROM usuarios u JOIN pedidos p ON u.id = p.usuario_id WHERE u.id = 1;

La tabla externa se itera una vez (1 fila cuando hay filtro por PK) y por cada fila se hace un Index Scan en la tabla interna. El costo es O(N × log M) si hay índice, O(N × M) si no.

⚠ Sin índice en la tabla interna, Nested Loop es catastrófico O(N×M)

Hash Join

Construye una tabla hash en memoria con la tabla más pequeña y luego escanea la tabla grande buscando coincidencias. Solo un escaneo de cada tabla.

EXPLAIN SELECT * FROM pedidos p JOIN clientes c ON p.cliente_id = c.id;

Hash Join construye la tabla hash de la relación más pequeña (build) y luego escanea la grande (probe). El costo es O(N+M) con un solo escaneo de cada tabla. Depende de work_mem para que la hash table quepa en memoria.

⚠ Si la hash table no cabe en work_mem, derrama a disco (batches múltiples) y se vuelve lento

Ejemplo paso a paso

1

Creamos una tabla de ejemplo con 100,000 filas y un índice

CREATE TABLE ejemplo (id SERIAL PRIMARY KEY, nombre TEXT, salario NUMERIC); INSERT INTO ejemplo SELECT generate_series(1,100000), 'Usuario_' || n, random()*5000 FROM generate_series(1,100000) n; CREATE INDEX idx_salario ON ejemplo (salario);
2

Ejecutamos EXPLAIN ANALYZE en una consulta con filtro por salario

EXPLAIN ANALYZE SELECT * FROM ejemplo WHERE salario > 4000;
3

PostgreSQL estima un 20% de selectividad (20,000 filas) y elige Seq Scan, pues supera el umbral de ~10-15% donde Index Scan es mejor

Seq Scan on ejemplo (cost=0.00..1896.00 rows=19648 width=42) Filter: (salario > 4000)
4

Si cambiamos el filtro a salario > 4900 (1% selectividad), PostgreSQL elige Index Scan

Index Scan using idx_salario on ejemplo (cost=0.29..124.50 rows=987 width=42) Index Cond: (salario > 4900)
5

Interpretación: El startup cost 0.29 es el costo de abrir el índice y navegar al primer nodo. El total cost 124.50 incluye la lectura de 987 filas del heap. El optimizador siempre elige el plan con menor costo total.

¿Qué tipo de nodo usaría PostgreSQL para una tabla pequeña de 100 filas sin índice?

Seq Scan Escaneo secuencial: lee toda la tabla bloque por bloque. Eficiente para tablas pequeñas o cuando necesitas >30% de las filas.
Index Scan Escaneo por índice: salta al árbol B, encuentra las filas. Ideal para búsquedas puntuales.
Bitmap Heap Scan Combina múltiples índices: construye un bitmap en memoria y luego lee los bloques. Balance entre selectividad y aleatoriedad.
Merge Join Junta dos conjuntos ordenados. Requiere datos pre-ordenados por ORDER BY o por índices.

Resumen del módulo

  • EXPLAIN muestra el plan de ejecución con costos startup, total y filas estimadas
  • Seq Scan es óptimo para tablas pequeñas o alta selectividad (>30%)
  • Index Scan brilla cuando recuperas pocas filas por un índice
  • Bitmap Heap Scan combina múltiples índices y lee en orden físico
  • Merge Join requiere datos ordenados; Hash Join construye una tabla en memoria; Nested Loop funciona con 1 fila externa + índice interno
  • El optimizador siempre elige el plan con menor costo total estimado
