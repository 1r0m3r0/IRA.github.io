📈 ANALYZE y Estadísticas

El maná del optimizador: histogramas, correlación y n_distinct

💡 Piénsalo así: ANALYZE es como el censo nacional. El gobierno necesita saber cuánta gente hay, cómo está distribuida por edad, región, ingresos, para tomar decisiones. PostgreSQL necesita saber cuántas filas hay, cómo se distribuyen los valores, para elegir el mejor plan de ejecución. Sin ANALYZE, el optimizador literalmente adivina.

¿Qué aprenderás?

  • A interpretar n_distinct, null_frac, correlation y most_common_freq

  • La diferencia entre default_statistics_target y muestreo
  • Cómo forzar ANALYZE manual y entender autovacuum

n_distinct

Número estimado de valores únicos en una columna. Es crítico para que el optimizador calcule la selectividad de condiciones de igualdad. Si n_distinct es 1000 en una columna con 1M filas, cada valor aparece ~1000 veces; el optimizador lo usa para estimar cuántas filas devolverá WHERE columna = X.

SELECT n_distinct FROM pg_stats WHERE tablename = 'clientes' AND attname = 'ciudad';

PostgreSQL estima n_distinct mediante muestreo estadístico (default 300 * default_statistics_target filas). Si el valor es negativo, indica la proporción: -0.1 significa ~10% de las filas son distintas.

⚠ Si n_distinct está infraestimado, el optimizador asume que el filtro devuelve demasiadas filas y elige Seq Scan en vez de Index Scan

null_frac

Fracción de valores nulos en la columna (0.0 a 1.0). Un valor de 0.15 significa que el 15% de las filas tienen NULL en esa columna. El optimizador lo usa para ajustar la estimación de filas en condiciones IS NULL, IS NOT NULL, y en joins.

SELECT null_frac FROM pg_stats WHERE tablename = 'pedidos' AND attname = 'fecha_envio';

Cuando null_frac es alto (>0.5), un índice en esa columna es menos eficiente porque muchas filas estarán agrupadas al final del índice. Para búsquedas NOT NULL, PostgreSQL sabe que debe saltarse esa fracción.

⚠ Si los nulos no son relevantes, considera CHECK CONSTRAINT NOT NULL para mejorar la calidad de las estadísticas

correlation

Coeficiente de correlación entre el orden físico de las filas en el heap y el orden lógico de los valores de la columna. Un valor cercano a 1.0 indica que los datos están físicamente ordenados como la columna; cercano a 0 indica distribución aleatoria. Afecta la decisión entre Index Scan y Bitmap Heap Scan.

SELECT correlation FROM pg_stats WHERE tablename = 'ventas' AND attname = 'fecha';

Si correlation es alta (>0.8), Index Scan es muy eficiente porque las filas consecutivas en el índice están cerca físicamente. Si es baja, Index Scan requiere muchos accesos aleatorios y Bitmap Heap Scan es preferible.

⚠ CLUSTER ordena físicamente la tabla por un índice, mejorando correlation drásticamente

most_common_freq (MCF)

Frecuencia de los valores más comunes en la columna. PostgreSQL guarda hasta default_statistics_target valores (default 100) con su frecuencia. Esto permite estimar con precisión filtros de igualdad sobre valores frecuentes sin depender de la aproximación de uniformidad.

SELECT most_common_vals, most_common_freqs FROM pg_stats WHERE tablename = 'clientes' AND attname = 'estatus';

Si el valor más común aparece en el 30% de las filas, el optimizador puede estimar exactamente 300K filas para WHERE estatus = 'activo' en una tabla de 1M.

⚠ Los histogramas (histogram_bounds) complementan MCF para distribuir el resto de valores menos comunes

default_statistics_target

Parámetro que controla la cantidad de muestreo para las estadísticas. Default es 100, lo que significa que ANALYZE muestrea 300 * 100 = 30,000 filas para cada columna. Subirlo a 500-1000 mejora la precisión a costa de tiempo de ANALYZE y tamaño de pg_stats.

ALTER TABLE clientes ALTER COLUMN salario SET STATISTICS 500;

Puedes ajustarlo por columna: salario puede necesitar más precisión que id. En PostgreSQL 19, el muestreo adaptativo permite mayor precisión con menos recursos.

⚠ Subir default_statistics_target globalmente a 1000 puede hacer ANALYZE 10x más lento

autovacuum + ANALYZE

autovacuum ejecuta ANALYZE automáticamente cuando el porcentaje de filas modificadas supera autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × filas. En tablas grandes, esto evita que las estadísticas queden desactualizadas.

SELECT relname, last_analyze, last_autoanalyze FROM pg_stat_all_tables WHERE schemaname = 'public';

Monitorea last_analyze y last_autoanalyze. Si ves que una tabla grande tiene last_analyze muy antiguo, ejecuta ANALYZE manualmente. Las estadísticas desactualizadas son la causa #1 de regresión de rendimiento.

⚠ Si autovacuum está desactivado, programa ANALYZE manual en ventanas de baja actividad

Ejemplo paso a paso

1

Creamos una tabla con 100,000 filas con distribución sesgada: algunos valores aparecen mucho más que otros

CREATE TABLE ventas (id SERIAL, producto TEXT, monto NUMERIC); INSERT INTO ventas SELECT n, CASE WHEN n%10=0 THEN 'Premium' WHEN n%5=0 THEN 'Regular' ELSE 'Económico' END, random()*1000 FROM generate_series(1,100000) n;
2

Ejecutamos ANALYZE para recolectar estadísticas

ANALYZE ventas;
3

Consultamos las estadísticas recolectadas para la columna producto

SELECT most_common_vals, most_common_freqs, n_distinct, null_frac FROM pg_stats WHERE tablename = 'ventas' AND attname = 'producto';
4

PostgreSQL sabe que 'Económico' aparece en ~70% de las filas. Un filtro WHERE producto='Premium' devolverá ~10% de filas (10,000). Con esta información, el optimizador decide si usar índice o escaneo secuencial.

EXPLAIN SELECT * FROM ventas WHERE producto = 'Premium'; -- ~10% filas → Index Scan probable EXPLAIN SELECT * FROM ventas WHERE producto = 'Económico'; -- ~70% filas → Seq Scan probable
5

Si insertamos 50,000 filas nuevas sin ANALYZE, las estadísticas quedan desactualizadas. El optimizador sigue pensando que hay 100K filas cuando hay 150K. Esto puede llevar a decisiones subóptimas.

INSERT INTO ventas SELECT n, 'Flash', random()*1000 FROM generate_series(1,50000) n; -- Las estadísticas aún muestran 0 para 'Flash'. ¡ANALYZE es necesario!

Resumen del módulo

  • ANALYZE recolecta estadísticas: n_distinct, null_frac, correlation, most_common_freqs
  • Sin ANALYZE, PostgreSQL usa valores aproximados de pg_class que pueden estar desactualizados
  • default_statistics_target (default 100) controla la precisión del muestreo estadístico
  • correlation alta (>0.8) favorece Index Scan; correlation baja favorece Bitmap Heap Scan
  • Las estadísticas desactualizadas son la causa #1 de regresión de rendimiento en producción
  • autovacuum ejecuta ANALYZE automáticamente; monitorea last_analyze en pg_stat_all_tables
