⚡ Parallel Query

Paraleliza consultas para aprovechar múltiples CPUs

💡 Piénsalo así: Parallel Query es como tener un equipo de cocineros en vez de uno solo. Un cocinero solo puede preparar una pizza a la vez. Con 4 cocineros, puedes preparar 4 pizzas simultáneamente. Pero ojo: no todas las recetas se pueden paralelizar (¿cómo cocinas una sopa entre 4?). PostgreSQL decide qué partes de la consulta se pueden repartir.

Gather / Gather Merge

El nodo Gather es el coordinador: lanza workers paralelos, cada worker ejecuta una parte del plan, y Gather recolecta los resultados. Gather Merge hace lo mismo pero preservando el orden.

Gather (cost=1000.00..5000.00 rows=50000 width=40) Workers Planned: 4 -> Parallel Seq Scan on ventas

El líder (leader) también participa como un worker adicional. Si hay 4 workers planificados, hay 5 procesos trabajando (leader + 4 workers). Cada worker escanea una porción diferente de la tabla.

⚠ Gather solo puede paralelizar si hay suficiente trabajo. Tablas pequeñas no se benefician del paralelismo

Parallel Seq Scan

El escaneo secuencial paralelo divide la tabla en bloques y asigna cada bloque a un worker. Cada worker escanea su bloque y filtra filas independientemente.

EXPLAIN SELECT count(*) FROM ventas WHERE monto > 1000;

PostgreSQL divide la tabla en chunks de ~1MB cada uno. Cada worker toma un chunk, lo escanea, filtra y cuenta. Al final Gather suma los conteos parciales. La escalabilidad depende de qué tan rápido se pueden dividir los bloques sin contención.

⚠ Parallel Seq Scan no funciona si la tabla es demasiado pequeña (< shared_buffers/8)

Parámetros de paralelismo

max_parallel_workers_per_gather (default 2): workers máximos por consulta. max_parallel_workers (default 8): workers totales del sistema. parallel_tuple_cost y parallel_setup_cost: penalización por paralelismo.

SET max_parallel_workers_per_gather = 4;

Incluso con muchos workers configurados, PostgreSQL solo paraleliza si el beneficio supera el overhead. parallel_setup_cost (default 1000) modela el costo de lanzar workers. parallel_tuple_cost (default 0.1) modela el costo de mover datos entre workers.

⚠ parallel_setup_cost muy alto desalienta el paralelismo. Si tienes CPUs rápidos, bájalo a 100 o menos

Ley de Amdahl

El speedup máximo está limitado por la porción secuencial del trabajo. Si el 30% de la consulta es secuencial (no paralelizable), el speedup máximo es 1/(0.3 + 0.7/N). Con N=∞ workers, máximo 3.33×.

speedup_max = 1 / (P_seq + P_par/N)

Para una consulta con 40% secuencial y 16 workers: speedup = 1/(0.4 + 0.6/16) = 2.29×. El 40% secuencial incluye: Gather, ordenamientos finales, funciones que no se pueden paralelizar.

⚠ Más workers no siempre es mejor. El overhead de coordinación puede superar la ganancia marginal

Operaciones NO paralelizables

Ciertas operaciones no pueden ejecutarse en paralelo: subconsultas correlacionadas, funciones marcadas como PARALLEL UNSAFE, cursores, FOR UPDATE, queries que modifican datos, y window functions con ORDER BY global.

-- PARALLEL UNSAFE function CREATE FUNCTION mi_func() RETURNS INT PARALLEL UNSAFE AS $$ ... $$;

Para verificar si una función es paralela: SELECT proparallel FROM pg_proc WHERE proname = 'func_name'; s = SAFE, r = RESTRICTED, u = UNSAFE. Las funciones de PL/pgSQL por defecto son UNSAFE (deben marcarse explícitamente).

⚠ Muchas funciones built-in son PARALLEL UNSAFE. string_agg, array_agg son RESTRICTED. Las funciones de window son generalmente UNSAFE

Paralelismo en Joins

Hash Join y Nested Loop se benefician del paralelismo: cada worker construye su parte de la hash table o escanea su porción. Parallel Hash Join construye una hash table compartida entre workers.

EXPLAIN SELECT /*+ Parallel(c 4) */ FROM clientes c JOIN pedidos p ...

Parallel Hash Join es la estrella del paralelismo en joins: todos los workers cooperan para construir y sondear la hash table. Parallel Nested Loop asigna diferentes filas externas a diferentes workers. Merge Join rara vez se paraleliza porque el orden debe preservarse.

⚠ Parallel Hash Join requiere que la hash table quepa en work_mem × workers. Si no, derrama a disco y el paralelismo empeora las cosas

Ejemplo paso a paso

1

Verificamos la configuración actual de paralelismo:

SHOW max_parallel_workers_per_gather; -- default 2 SHOW max_parallel_workers; -- default 8 SHOW parallel_setup_cost; -- default 1000 SHOW parallel_tuple_cost; -- default 0.1
2

Ejecutamos un count(*) en una tabla grande para ver el plan paralelo:

EXPLAIN ANALYZE SELECT count(*) FROM ventas WHERE monto > 500;
3

Observamos el plan: Parallel Seq Scan + Finalize Aggregate. Gather recolecta los conteos parciales.

Finalize Aggregate (cost=4520.00..4520.01 rows=1 width=8) -> Gather (cost=4510.00..4519.00 rows=4 width=8) Workers Planned: 4 -> Partial Aggregate (cost=3510.00..3510.01 rows=1 width=8) -> Parallel Seq Scan on ventas (cost=0.00..3510.00 rows=100000 width=6)
4

Para consultas OLTP, el paralelismo puede no activarse. Forzamos el plan:

SET parallel_setup_cost = 0; -- elimina la penalización de setup SET min_parallel_table_scan_size = 0; -- paraleliza tablas de cualquier tamaño
5

Monitoreamos el uso real de workers con pg_stat_activity:

SELECT state, wait_event, query FROM pg_stat_activity WHERE backend_type LIKE 'parallel worker%'; -- Muestra los workers activos y qué están ejecutando

Resumen del módulo

  • Gather/Gather Merge lanzan workers paralelos y recolectan resultados
  • El speedup sigue la Ley de Amdahl: la porción secuencial limita la ganancia máxima
  • No todas las operaciones se paralelizan: funciones UNSAFE, cursores, FOR UPDATE no
  • Parallel Hash Join permite joins paralelos eficientes con hash table compartida
  • Configura max_parallel_workers_per_gather = número de cores - 1 para uso general
  • Monitorea workers en pg_stat_activity para diagnosticar problemas de paralelismo
