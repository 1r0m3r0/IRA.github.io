🧹 REINDEX / VACUUM y Bloat

Combate la inflación de tu base de datos

💡 Piénsalo así: El bloat en PostgreSQL es como tu refrigerador: con el tiempo se acumulan sobras viejas (tuplas muertas) que ocupan espacio. VACUUM es como limpiar el refri una vez por semana. REINDEX es como reorganizar los estantes. autovacuum es como tener un robot que limpia automáticamente. Si no limpias, el refri se llena de cosas que ya no sirven y no encuentras lo que buscas.

¿Qué es el Bloat?

Bloat es espacio ocupado por tuplas muertas (versiones antiguas de filas) que MVCC mantiene para transacciones concurrentes. Cada UPDATE crea una nueva versión de la fila; la anterior queda como "tupla muerta". Con el tiempo, estas tuplas muertas se acumulan y la tabla crece más de lo necesario.

SELECT n_live_tup, n_dead_tup, n_dead_tup::float/nullif(n_live_tup,0)*100 AS bloat_pct FROM pg_stat_all_tables WHERE relname = 'pedidos';

Un bloat >20% empieza a degradar el rendimiento. Las consultas tienen que escanear más páginas para encontrar las mismas filas.

⚠ El bloat también afecta los índices: pueden tener entradas apuntando a tuplas muertas

VACUUM estándar

VACUUM (sin FULL) escanea las páginas de la tabla, marca el espacio de las tuplas muertas como reusable, y actualiza el mapa de visibilidad (VM). No comprime la tabla ni devuelve espacio al sistema operativo, pero permite que las nuevas inserciones reutilicen el espacio.

VACUUM pedidos;

El VM permite a Index Only Scan evitar verificar la visibilidad de las filas. VACUUM es rápido y no bloquea lecturas/escrituras concurrentes. Debe ejecutarse periódicamente (autovacuum lo hace).

⚠ Si nunca ejecutas VACUUM, el XID puede wraparound y forzar un shutdown

VACUUM FULL

VACUUM FULL reescribe completamente la tabla, eliminando todo el bloat y devolviendo espacio al sistema operativo. Es equivalente a CLUSTER sin ordenar. Durante su ejecución, bloquea la tabla con un ACCESS EXCLUSIVE LOCK.

VACUUM FULL pedidos;

Útil cuando has eliminado muchas filas (DELETE masivo) y necesitas recuperar espacio en disco. Pero cuidado: puede tomar mucho tiempo y bloquea toda la actividad en la tabla.

⚠ En tablas grandes (>10 GB), programa VACUUM FULL en ventanas de mantenimiento

REINDEX

REINDEX reconstruye uno o todos los índices de una tabla desde cero. Los índices también sufren bloat: al eliminar filas, las entradas del índice no se limpian inmediatamente. Con el tiempo, el índice ocupa más espacio del necesario y la navegación es más lenta.

REINDEX INDEX idx_pedidos_fecha;

En PostgreSQL 19, REINDEX es más eficiente que en versiones anteriores: requiere menos WAL y menos trabajo de mantenimiento. El índice reconstruido es compacto y eficiente.

⚠ REINDEX estándar bloquea escrituras en el índice. Usa REINDEX CONCURRENTLY para producción

REINDEX CONCURRENTLY

REINDEX CONCURRENTLY (disponible desde PG12+) reconstruye el índice sin bloquear escrituras concurrentes. Crea un índice nuevo en paralelo, luego intercambia y elimina el antiguo. Requiere más espacio en disco y toma más tiempo, pero no afecta la disponibilidad.

REINDEX INDEX CONCURRENTLY idx_pedidos_fecha;

Es la opción recomendada para producción: cero downtime. PostgreSQL 19 mejoró el rendimiento de CONCURRENTLY reduciendo el tiempo de construcción.

⚠ Si falla, deja un índice "invalid". Debes eliminarlo manualmente con DROP INDEX

Monitoreo de Bloat

Existen consultas en pg_stat_all_tables y pg_class para estimar el bloat. También puedes usar extensiones como pgstattuple para medir el espacio exacto ocupado por tuplas vivas vs muertas.

SELECT relname, pg_size_pretty(pg_relation_size(relid)), n_dead_tup FROM pg_stat_all_tables WHERE n_dead_tup > 10000 ORDER BY n_dead_tup DESC;

La herramienta pg_bloat_check (pg_stat_all_tables + pg_class) estima el bloat basado en la diferencia entre el tamaño real de la tabla y el tamaño esperado. Ideal para dashboards de monitoreo.

⚠ Configura alertas cuando n_dead_tup supere 20% de n_live_tup

Ejemplo paso a paso

1

Creamos una tabla con 10,000 filas, un índice y verificamos el tamaño

CREATE TABLE test_bloat (id SERIAL, dato TEXT, fecha TIMESTAMP DEFAULT now()); INSERT INTO test_bloat SELECT n, md5(random()::text), now() FROM generate_series(1,10000) n; CREATE INDEX idx_bloat_fecha ON test_bloat (fecha); SELECT pg_size_pretty(pg_relation_size('test_bloat')) AS tabla_size, pg_size_pretty(pg_relation_size('idx_bloat_fecha')) AS idx_size;
2

Simulamos actividad: 50,000 updates que generan tuplas muertas (MVCC)

UPDATE test_bloat SET dato = md5(random()::text) WHERE id <= 5000; -- 5000 nuevas versiones DELETE FROM test_bloat WHERE id % 10 = 0; -- 1000 filas eliminadas
3

Verificamos las tuplas muertas acumuladas

SELECT n_live_tup, n_dead_tup, (n_dead_tup::float/nullif(n_live_tup,0))*100 AS bloat_pct FROM pg_stat_all_tables WHERE relname = 'test_bloat';
4

Ejecutamos VACUUM para marcar las tuplas muertas como espacio reusable

VACUUM test_bloat; SELECT n_dead_tup FROM pg_stat_all_tables WHERE relname = 'test_bloat'; -- debería ser 0
5

Reconstruimos el índice para eliminar el bloat del índice y compactarlo

REINDEX INDEX CONCURRENTLY idx_bloat_fecha; SELECT pg_size_pretty(pg_relation_size('idx_bloat_fecha')) AS idx_size_compactado; -- El tamaño del índice debería haber disminuido significativamente

Resumen del módulo

  • Bloat es espacio ocupado por tuplas muertas (MVCC). >20% degrada el rendimiento de consultas e índices
  • VACUUM marca tuplas muertas como reutilizables; es rápido y no bloquea lecturas/escrituras
  • VACUUM FULL reescribe la tabla y devuelve espacio al SO, pero bloquea la tabla con ACCESS EXCLUSIVE
  • REINDEX reconstruye índices inflados; REINDEX CONCURRENTLY lo hace sin bloqueos
  • autovacuum ejecuta VACUUM automáticamente; configura autovacuum_vacuum_scale_factor para tablas grandes
  • Monitorea n_dead_tup en pg_stat_all_tables para detectar bloat temprano
