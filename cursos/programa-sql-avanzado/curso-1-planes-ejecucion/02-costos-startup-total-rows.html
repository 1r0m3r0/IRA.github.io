📊 Costos startup / total / rows

Descifra los tres números mágicos del plan de ejecución

💡 Piénsalo así: Los costos en EXPLAIN son como el GPS de tu viaje. El startup cost es el tiempo hasta que arrancas el auto y llegas a la autopista. El total cost es el tiempo total estimado del viaje. Y rows es el número de pasajeros que esperas recoger. Si el GPS subestima los pasajeros, llegarás tarde.

¿Qué aprenderás?

  • A interpretar los tres números que muestra EXPLAIN: startup cost, total cost, rows
  • Cómo el optimizador calcula los costos según páginas, filas y CPU
  • Por qué un plan con menor startup cost puede ser peor a largo plazo
  • A estimar manualmente el costo de una consulta simple
  • Cómo la selectividad del filtro afecta los costos totales

Startup Cost

Costo inicial antes de producir la primera fila. Incluye abrir archivos, leer el primer bloque del índice, o construir la tabla hash. Un startup alto significa que la consulta tarda en arrancar pero puede ser eficiente después.

Hash Join (cost=10.00..100.00 rows=500 width=40)

El 10.00 es el startup: tiempo para construir la hash table en memoria. Si la consulta se cancela antes de las primeras filas, ese trabajo se pierde.

⚠ Para consultas OLTP que necesitan la primera fila rápido, prefiere planes con bajo startup

Total Cost

Costo total estimado para producir todas las filas del plan. Es la suma del startup más el costo de procesar cada fila (cpu_tuple_cost, cpu_operator_cost) y cada página (seq_page_cost, random_page_cost).

Seq Scan on orders (cost=0.00..1896.00 rows=100000 width=36)

1896.00 = 0.00 + (100000 páginas × 1.0) + (100000 filas × 0.01). El optimizador compara este número con otros planes para elegir el más barato.

⚠ Total cost no es tiempo real, es una unidad adimensional que solo sirve para comparar planes

Estimated Rows

Número estimado de filas que devolverá el nodo. Basado en estadísticas de la tabla (pg_class.reltuples) y la selectividad del filtro. Es la estimación más crítica: si falla, el plan puede ser pésimo.

-> Seq Scan on usuarios (cost=0.00..124.50 rows=987 width=42)

987 filas estimadas de 100,000 totales = 0.987% selectividad. Si en realidad hay 50,000 filas, el plan óptimo sería diferente.

⚠ Estadísticas desactualizadas → rows mal estimadas → plan subóptimo. Ejecuta ANALYZE regularmente

Selectividad

Fracción de filas que pasa el filtro. Es la variable más importante en la estimación de costos. Una selectividad de 0.01 (1%) produce muy pocas filas, haciendo que Index Scan sea mejor que Seq Scan.

SELECT * FROM productos WHERE precio > 500; -- selectividad estimada 15%

El optimizador usa histogramas y most_common_values de pg_stats para estimar la selectividad. Si el histograma está desactualizado, la estimación falla.

⚠ La selectividad depende de la distribución real de datos, no del número total de filas

random_page_cost vs seq_page_cost

seq_page_cost (1.0) es el costo de leer una página secuencialmente. random_page_cost (4.0) es el costo de una lectura aleatoria. En SSD modernos, reduce random_page_cost a 1.1 para reflejar mejor el hardware.

SET random_page_cost = 1.1; -- para SSD NVMe

Con random_page_cost=4, el optimizador penaliza los Index Scan que hacen accesos aleatorios. Bajarlo a 1.1 hace que PostgreSQL use más índices, lo que suele ser correcto en SSD.

⚠ Usar random_page_cost=4 en SSD causa que PostgreSQL subestime los Index Scan. ¡Ajusta este parámetro!

cpu_tuple_cost y cpu_operator_cost

Parámetros que modelan el costo de CPU por fila procesada y por operación ejecutada. Por defecto: cpu_tuple_cost=0.01, cpu_operator_cost=0.0025. Ajustarlos cambia la preferencia entre escaneos secuenciales y por índice.

EXPLAIN (COSTS TRUE) SELECT count(*) FROM ventas;

Aggregate usa cpu_operator_cost para estimar el costo de la función count(). Si tienes CPUs muy rápidos, bajar estos valores hace que PostgreSQL paralelice más agresivamente.

⚠ No ajustes cpu_tuple_cost sin entender el impacto. Cambia el balance entre Seq Scan y Index Scan

Ejemplo paso a paso

1

Ejecutamos EXPLAIN en una consulta simple y analizamos cada número

EXPLAIN SELECT * FROM pedidos WHERE total > 100;
2

PostgreSQL responde con el plan de ejecución. Ejemplo típico:

Seq Scan on pedidos (cost=0.00..3450.00 rows=15000 width=40) Filter: (total > 100)
3

Startup cost 0.00: Seq Scan no necesita preparación, empieza a leer desde el primer bloque. Total cost 3450.00: incluye lectura de todas las páginas + CPU por cada fila. Rows 15000: estimación de filas que pasan el filtro.

4

Si hay un índice en total, con selectividad baja el plan cambia:

Index Scan using idx_pedidos_total on pedidos (cost=0.29..85.50 rows=150 width=40) Index Cond: (total > 1000)
5

Startup 0.29 > 0.00 porque abrir el índice cuesta. Pero total 85.50 << 3450.00 porque solo lee 150 filas. El optimizador compara: ¿3450.00 > 85.50? Sí → elige Index Scan. Así de simple funciona la decisión.

Resumen del módulo

  • Startup cost: costo antes de producir la primera fila. Bajo para Seq Scan, más alto para planes que requieren preparación
  • Total cost: suma del startup + costo por fila/página. El optimizador elige el plan con menor total cost
  • Rows: estimación crítica de filas. Si está desactualizada, el plan será subóptimo
  • Los costos son unidades adimensionales, no tiempo real. Solo sirven para comparar planes entre sí
  • random_page_cost debe ajustarse a 1.1 para SSD para que PostgreSQL use más índices
  • La selectividad del filtro es el factor más determinante en la estimación de filas
