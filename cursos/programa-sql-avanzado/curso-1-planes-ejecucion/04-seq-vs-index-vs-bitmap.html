📡 Seq Scan vs Index Scan vs Bitmap

Comparamos los tres escaneos en velocidad y eficiencia

💡 Piénsalo así: Seq Scan es como leer un libro entero para encontrar una palabra. Index Scan es como usar el índice al final del libro para ir directo a la página. Bitmap Scan es como marcar varias páginas con post-its y luego ir a leer solo esas.

  • Por qué Bitmap Scan combina lo mejor de ambos mundos
  • A visualizar cómo cada escaneo recorre los bloques de la tabla

Seq Scan

Escaneo secuencial: lee todos los bloques de la tabla en orden físico, del primero al último. Ignora índices y filtros hasta después de leer. Simple y predecible.

EXPLAIN SELECT * FROM tabla_grande WHERE activo = true;

El costo es seq_page_cost × páginas + cpu_tuple_cost × filas. No depende de índices ni de filtros. Excelente cuando recuperas >30% de las filas, porque los accesos secuenciales son mucho más rápidos que los aleatorios (especialmente en HDD).

⚠ En tablas muy grandes con filtros selectivos, Seq Scan lee miles de páginas innecesarias

Index Scan

Navega el árbol B+ del índice para localizar exactamente las filas que cumplen la condición. Combina búsqueda en el índice + acceso aleatorio al heap.

EXPLAIN SELECT * FROM usuarios WHERE email = 'user@ejemplo.com';

Costo = random_page_cost × (altura_árbol + filas_estimadas) + cpu_operator_cost. Cada fila requiere un acceso aleatorio al heap. Ideal para búsquedas con alta selectividad (<5% de filas). En SSD, los accesos aleatorios son casi tan rápidos como secuenciales, lo que favorece a Index Scan.

⚠ Con random_page_cost=4 en SSD, PostgreSQL subestima Index Scan. Bájalo a 1.1

Bitmap Heap Scan

Combina las ventajas de índice y acceso secuencial. Primero construye un bitmap de bloques (no filas) y luego lee los bloques en orden, descomprimiendo las filas válidas.

EXPLAIN SELECT * FROM ventas WHERE fecha > '2024-01-01' AND region = 'Norte';

Dos fases: (1) Bitmap Index Scan en cada condición → bitmap de bloques. (2) AND/OR combina bitmaps → Bitmap Heap Scan lee bloques en orden. Excelente para selectividad media (5-30%) o cuando múltiples condiciones usan índices separados.

⚠ Cada bitmap aumenta el overhead de memoria. Si hay muchos, PostgreSQL puede preferir Seq Scan

Index Only Scan

Cuando todas las columnas necesarias están en el índice, PostgreSQL no toca el heap. Es el escaneo más rápido porque solo lee el índice, que es mucho más pequeño que la tabla.

EXPLAIN SELECT id, email FROM usuarios WHERE email > 'a%';

El índice contiene (email, id). Si SELECT solo pide esas columnas, PostgreSQL nunca visita el heap. Esto reduce drásticamente los accesos aleatorios. Para que funcione, el índice debe cubrir todas las columnas del SELECT más las del WHERE.

⚠ PostgreSQL debe verificar visibilidad con el mapa de visibilidad. Si hay filas no visibles, cae a Index Scan

Frozen Pages

Las páginas congeladas (pg_frozen) solo contienen filas visibles para todas las transacciones. El mapa de visibilidad permite a Index Only Scan saltarse la verificación de visibilidad.

VACUUM FREEZE; -- congela todas las tuplas viejas

Cuando una página está marcada como "totalmente visible" en el visibility map, PostgreSQL confía en que todas las filas son visibles y no necesita verificar el heap. Esto hace que Index Only Scan sea aún más rápido. VACUUM regular actualiza este mapa.

⚠ Tablas con muchas actualizaciones tienen pocas páginas congeladas, reduciendo la eficacia de Index Only Scan

Ejemplo paso a paso

1

Creamos una tabla ventas con 1M filas y varios índices

CREATE TABLE ventas (id SERIAL, fecha DATE, monto NUMERIC, region TEXT); INSERT INTO ventas SELECT generate_series(1,1000000), '2024-01-01'::date + (random()*365)::int, random()*5000, (ARRAY['Norte','Sur','Este','Oeste'])[ceil(random()*4)]; CREATE INDEX idx_fecha ON ventas(fecha); CREATE INDEX idx_monto ON ventas(monto);
2

Probamos SELECT * con filtro de alta selectividad (0.1%):

EXPLAIN SELECT * FROM ventas WHERE fecha = '2024-06-15'; -- Index Scan: encuentra ~3 filas por índice, 3 accesos aleatorios al heap
3

Filtro de media selectividad (10%):

EXPLAIN SELECT * FROM ventas WHERE fecha > '2024-12-01'; -- Bitmap Heap Scan: marca 10% de bloques, los lee en orden secuencial
4

Filtro de baja selectividad (>50%):

EXPLAIN SELECT * FROM ventas WHERE monto > 0; -- Seq Scan: mejor leer toda la tabla secuencialmente que hacer millones de accesos aleatorios
5

Caso especial: Index Only Scan con covering index:

CREATE INDEX idx_cubrimos ON ventas(fecha) INCLUDE (monto); EXPLAIN SELECT fecha, monto FROM ventas WHERE fecha > '2024-12-01'; -- Index Only Scan: no toca el heap porque el índice tiene fecha y monto

Resumen del módulo

  • Seq Scan: lee toda la tabla. Óptimo para >30% de filas o tablas pequeñas
  • Index Scan: busca por índice + acceso aleatorio al heap. Óptimo para <5% de filas
  • Bitmap Heap Scan: construye bitmap de bloques y lee en orden. Óptimo para 5-30% de filas
  • Index Only Scan: no toca el heap si el índice cubre todas las columnas. El más rápido
  • random_page_cost debe ajustarse a 1.1 en SSD para que el optimizador use índices correctamente
  • El mapa de visibilidad (VACUUM) hace que Index Only Scan evite verificaciones de visibilidad
