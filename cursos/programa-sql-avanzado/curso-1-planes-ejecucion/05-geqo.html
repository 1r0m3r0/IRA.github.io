🧬 GEQO - Genetic Query Optimizer

El algoritmo genético para optimizar joins complejos

💡 Piénsalo así: GEQO es como la evolución de las especies aplicada a bases de datos. Cuando tienes muchas tablas (>12), evaluar todas las combinaciones posibles es como buscar una aguja en un pajar cósmico. En vez de eso, GEQO "cría" generaciones de planes de ejecución, cruzando los mejores y mutándolos, hasta encontrar uno bueno.

Problema de las N tablas

El número de planes posibles para N tablas es N! (factorial). Para 8 tablas: 40,320 planes. Para 12 tablas: 479 millones. Para 20 tablas: 2.43 × 10¹⁸. Evaluarlos todos es computacionalmente imposible.

-- 12 tablas → 479,001,600 combinaciones de join posibles

El optimizador exhaustivo (default) evalúa recursivamente todas las combinaciones. El costo de optimización crece factorialmente. Por eso PostgreSQL cambia a GEQO automáticamente cuando hay más de 12 tablas (parámetro geqo_threshold).

⚠ Con 12 tablas exactas, GEQO puede activarse si hay subconsultas que aumentan el conteo efectivo

Selección Natural

GEQO genera una población inicial aleatoria de planes de ejecución. Evalúa su costo total y selecciona los mejores como "padres". Los padres se cruzan para producir hijos, combinando fragmentos de cada plan.

geqo_pool_size = 1000 -- tamaño de la población geqo_generations = 500 -- número de generaciones

Cada plan se representa como un cromosoma: una permutación del orden de las tablas. El cruce mezcla dos permutaciones. La mutación intercambia dos tablas aleatoriamente. Después de suficientes generaciones, emerge un plan de bajo costo.

⚠ GEQO no garantiza el plan óptimo global, solo uno "suficientemente bueno"

Cruce y Mutación

El operador de cruce (PMX - Partially Mapped Crossover) toma dos planes padres y combina segmentos. La mutación intercambia dos tablas en la permutación. La élite (mejores planes) sobrevive intacta cada generación.

Padre 1: [A,B,C,D,E] Padre 2: [E,D,C,B,A] Hijo: [A,D,C,B,E] -- segmento central del padre 2, extremos del padre 1

La presión selectiva asegura que los planes de bajo costo se reproduzcan más. Con el tiempo, la población converge hacia buenas soluciones. El elitismo preserva los mejores planes para que no se pierdan por mutación.

⚠ Poblaciones pequeñas (<100) convergen rápido pero a soluciones pobres

geqo_threshold

Parámetro que define cuándo activar GEQO. Por defecto: 12. Si pones 15, el optimizador exhaustivo evaluará hasta 15 tablas (1.3 billones de planes). Si pones 8, GEQO se activa antes, ahorrando tiempo de optimización.

SET geqo_threshold = 10; -- GEQO se activa con 10+ tablas

Para consultas OLTP con joins predecibles, GEQO puede ser contraproducente porque el plan exhaustivo es conocido. Para consultas analíticas con muchas tablas, GEQO es esencial. El threshold óptimo depende de la complejidad típica de tus consultas.

⚠ Bajar geqo_threshold a 8 acelera la optimización pero puede producir planes peores

pg_hint_plan

Extensión que permite forzar planes de ejecución manualmente. Cuando GEQO produce un plan subóptimo, puedes usar hints para guiar al optimizador hacia un mejor plan.

/*+ Leading((t1 t2) t3) HashJoin(t1 t2) */

Los hints permiten especificar el orden de joins, el tipo de join y los índices a usar. Es la solución definitiva cuando GEQO se equivoca. Muy usado en data warehouses con consultas complejas de 20+ tablas.

⚠ pg_hint_plan requiere instalación y mantenimiento. Los hints pueden quedar obsoletos si cambian los datos

Ejemplo paso a paso

1

Una consulta con 15 tablas en JOIN. GEQO se activa automáticamente.

SELECT * FROM t1 JOIN t2 ON ... JOIN t3 ON ... JOIN t4 ON ... JOIN t5 ON ... JOIN t6 ON ... JOIN t7 ON ... JOIN t8 ON ... JOIN t9 ON ... JOIN t10 ON ... JOIN t11 ON ... JOIN t12 ON ... JOIN t13 ON ... JOIN t14 ON ... JOIN t15 ON ...;
2

GEQO genera una población inicial de 1000 planes aleatorios. Evalúa el costo de cada uno y selecciona los 100 mejores como padres.

3

Durante 500 generaciones, los planes se cruzan y mutan. Cada generación produce 1000 hijos. El mejor plan de cada generación se preserva (elitismo).

4

GEQO converge a un plan con costo total estimado. PostgreSQL lo ejecuta. El resultado no es el plan óptimo global, pero se acerca (típicamente dentro del 10-20% del óptimo).

5

Si el plan es subóptimo, instala pg_hint_plan y fuerza el orden de joins:

LOAD 'pg_hint_plan'; SET pg_hint_plan.enable_hint = on; /*+ Leading((t1 (t2 t3) (t4 t5))) */ SELECT ...

Resumen del módulo

  • GEQO resuelve el problema factorial de los joins: N! crece más rápido que cualquier mejora de hardware
  • Usa selección natural: genera, evalúa, cruza y muta planes de ejecución
  • Se activa automáticamente con >12 tablas (geqo_threshold)
  • No garantiza el plan óptimo global, solo uno suficientemente bueno (~10-20% del óptimo)
  • Para consultas OLTP con joins fijos, conviene desactivar GEQO o subir el threshold
  • pg_hint_plan permite forzar manualmente el plan cuando GEQO se equivoca
