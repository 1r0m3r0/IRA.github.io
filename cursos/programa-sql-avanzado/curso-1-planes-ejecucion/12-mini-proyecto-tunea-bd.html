Diagnóstico con EXPLAIN

El primer paso siempre es ejecutar EXPLAIN (ANALYZE, BUFFERS) en la consulta lenta. Identifica el nodo de mayor costo total y el que consume más tiempo real (actual time). Busca Seq Scan en tablas grandes (>100K filas), Hash Join con múltiples batches, o Sort que derraman a disco.

EXPLAIN (ANALYZE, BUFFERS) SELECT c.nombre, COUNT(p.id) FROM clientes c JOIN pedidos p ON p.cliente_id = c.id WHERE c.activo = true GROUP BY c.nombre;

El diagnóstico típico: un Seq Scan en clientes (sin índice en activo) y un Hash Join que derrama a disco (work_mem insuficiente).

⚠ Sin BUFFERS no ves cuántas páginas leyó ni si hubo lecturas compartidas vs locales

Ajuste de work_mem

work_mem controla la memoria disponible para operaciones de sort, hash tables y bitmap operations. Si es insuficiente, PostgreSQL derrama a disco usando archivos temporales, lo que multiplica el tiempo de ejecución por 10-100x.

SET work_mem = '64MB'; EXPLAIN ANALYZE SELECT * FROM pedidos ORDER BY monto DESC; -- Sort Method: quicksort Memory: 32kB

Monitorea Sort Method: si ves "external merge Disk", necesitas más work_mem. Para sort en memoria, quicksort usa ~memory: X kB. Si derrama, aparece "external sort Disk: Y kB".

⚠ work_mem es por operación, no por sesión. 100 conexiones × 64MB = 6.4GB potencial

Creación de Índices Estratégicos

Los índices no son universales: hay que crearlos donde el optimizador los usará. Busca condiciones WHERE, JOIN y ORDER BY en columnas con alta selectividad (<10%). Un índice compuesto (col1, col2) puede eliminar Sort adicionales.

CREATE INDEX idx_clientes_activo ON clientes (activo) WHERE activo = true; -- índice parcial CREATE INDEX idx_pedidos_cliente ON pedidos (cliente_id, fecha); -- índice compuesto

El índice parcial idx_clientes_activo solo indexa filas con activo=true, reduciendo el tamaño del índice. El compuesto permite Index Only Scan si SELECT solo pide cliente_id y fecha.

⚠ Demasiados índices ralentizan INSERT/UPDATE/DELETE. Elige solo los que más beneficien tus consultas

Configuración de Paralelismo

max_parallel_workers_per_gather controla cuántos workers pueden escanear una tabla en paralelo. Para tablas grandes (>1M filas), el paralelismo puede reducir el tiempo de 10s a 2s. Pero no todas las consultas se benefician: OLTP empeora.

SET max_parallel_workers_per_gather = 4; EXPLAIN ANALYZE SELECT count(*), AVG(monto) FROM pedidos WHERE fecha > '2024-01-01';

Busca "Gather" o "Parallel Seq Scan" en el plan. Si ves workers planeados=0, la consulta no es paralelizable (funciones UNSAFE, FOR UPDATE, cursores).

⚠ Ley de Amdahl: si la parte secuencial es 20%, la ganancia máxima con 4 workers es 3.3x

VACUUM y Bloat

El bloat hace que las consultas escaneen páginas innecesarias. Una tabla con 40% bloat tiene 40% más páginas que leer, lo que aumenta el tiempo de Seq Scan y hace que Index Scan sea menos eficiente por la correlación dañada.

VACUUM ANALYZE pedidos; SELECT pg_size_pretty(pg_relation_size('pedidos')) AS antes; VACUUM FULL pedidos; SELECT pg_size_pretty(pg_relation_size('pedidos')) AS despues;

VACUUM ANALYZE combina la limpieza con la actualización de estadísticas. VACUUM FULL recupera espacio físico pero bloquea la tabla. La diferencia de tamaño antes/después es el bloat recuperado.

⚠ Si ves autovacuum corriendo constantemente, ajusta autovacuum_vacuum_scale_factor para tablas grandes

Medición de Mejora

La única métrica que importa es el tiempo de ejecución de la consulta con EXPLAIN ANALYZE real (no solo estimado). Mide antes y después de cada optimización. Lleva un registro: diagnóstico, acción tomada, tiempo antes, tiempo después.

EXPLAIN ANALYZE SELECT ... ; -- Antes: 12,432 ms -- Crear índice, ajustar work_mem, VACUUM EXPLAIN ANALYZE SELECT ... ; -- Después: 843 ms

La mejora de 12s a 0.8s es un ~93% de reducción. El objetivo no es "optimizar" para tener el plan perfecto, sino reducir el tiempo de la consulta al mínimo aceptable para el negocio.

⚠ Mide 3 veces cada consulta (cache fría, media y caliente) para obtener datos representativos

Ejemplo paso a paso

1

Diagnóstico inicial: ejecutamos EXPLAIN ANALYZE en la consulta lenta

EXPLAIN (ANALYZE, BUFFERS) SELECT c.nombre, COUNT(p.id), AVG(p.monto) FROM clientes c LEFT JOIN pedidos p ON p.cliente_id = c.id WHERE c.activo = true AND p.fecha >= '2024-01-01' GROUP BY c.nombre ORDER BY COUNT(p.id) DESC LIMIT 10;
2

Identificamos tres problemas: Seq Scan en clientes (sin filtro por activo), Hash Join derramando a disco (work_mem pequeño), y Sort externo

Seq Scan on clientes (cost=0.00..4567.00 rows=500000 width=...) Filter: activo = true Hash Join (cost=1234..15678 rows=345000 width=...) Hash Batches: 64 (work_mem insuficiente) Sort Method: external merge Disk: 1234kB
3

Aplicamos las correcciones: índice parcial en clientes.activo, subimos work_mem a 64MB, creamos índice en pedidos(cliente_id, fecha)

CREATE INDEX idx_clientes_activos ON clientes (id) WHERE activo = true; SET work_mem = '64MB'; CREATE INDEX idx_pedidos_cliente_fecha ON pedidos (cliente_id, fecha);
4

Ejecutamos VACUUM ANALYZE en ambas tablas para actualizar estadísticas y limpiar bloat

VACUUM ANALYZE clientes, pedidos;
5

Re-ejecutamos la consulta: ahora vemos Index Scan en ambas tablas, Hash Join en memoria (1 batch), y Sort en memoria. El tiempo bajó de 12s a 0.8s - ¡misión cumplida!

Index Only Scan using idx_pedidos_cliente_fecha on pedidos (cost=0.29..123.50 rows=9876 width=...) Hash Join (cost=456..2345 rows=9876 width=...) Hash Batches: 1 Sort Method: quicksort Memory: 356kB
