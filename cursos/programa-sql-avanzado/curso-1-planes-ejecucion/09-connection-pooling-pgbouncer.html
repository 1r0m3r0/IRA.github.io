🔌 Connection Pooling con PgBouncer

Más conexiones no siempre es mejor. Pooléalas.

💡 Piénsalo así: PgBouncer es como el recepcionista de un gimnasio. En vez de dejar que 500 personas entren al mismo tiempo (colapsando las máquinas), el recepcionista deja pasar solo a 50 y el resto espera en la sala. Cuando alguien termina, pasa el siguiente. Así el gimnasio (PostgreSQL) nunca se satura.

¿Qué aprenderás?

  • Cómo calcular el pool size óptimo según CPUs
  • Configuración básica de PgBouncer para producción

El problema de las conexiones

Cada conexión PostgreSQL consume ~10MB de RAM (shared memory + backend process). Con 500 conexiones, eso son 5GB solo para mantenerlas abiertas, sin ejecutar consultas. Además, PostgreSQL crea un proceso por conexión (no hilos), lo que añade overhead de scheduling.

SELECT count(*) FROM pg_stat_activity; -- conexiones activas -- Cada backend process consume ~5-10MB

PostgreSQL maneja bien hasta ~200 conexiones. Más allá, la contención de locks de memoria (spinlocks en shared_buffers) degrada el rendimiento drásticamente. La solución es PgBouncer: mantiene las conexiones reales en un pool pequeño y las reasigna entre los clientes.

⚠ Cada conexión PostgreSQL = un proceso del sistema operativo. 1000 conexiones = 1000 procesos compitiendo por CPU

Transaction Pooling

PgBouncer en modo transacción asigna la conexión al cliente solo durante una transacción. Cuando el cliente hace COMMIT/ROLLBACK, la conexión vuelve al pool. El siguiente cliente la reusa. Esto permite manejar miles de clientes con ~50 conexiones.

pool_mode = transaction -- en pgbouncer.ini

Después de cada transacción, se limpia el estado de la sesión (SET, PREPARE, LISTEN, etc.). Las aplicaciones deben ser conscientes de que las conexiones cambian entre transacciones. No puedes asumir que SET persiste entre transacciones; cada transacción empieza "limpia".

⚠ Las variables de sesión (SET), prepared statements, y advisory locks no persisten entre transacciones con transaction pooling

Session Pooling

Modo sesión: la conexión se asigna a un cliente hasta que se desconecta. Más simple pero menos eficiente. Si tienes 1000 clientes, necesitas 1000 conexiones en el pool (o los clientes esperan).

pool_mode = session -- en pgbouncer.ini

Session pooling mantiene el estado de la sesión: SET, prepared statements, cursor abiertos, etc. La aplicación funciona como si estuviera conectada directamente a PostgreSQL. El pool limita el número máximo de conexiones simultáneas, pero igual necesitas suficientes para no bloquear clientes.

⚠ Session pooling no escala tan bien como transaction pooling. Úsalo solo cuando la app no soporte transaction pooling

Pool Size óptimo

El tamaño del pool se calcula según CPUs: pool_size = (2.5 × cores) para IO-bound, (cores + 1) para CPU-bound. Para servidores modernos con 8 cores: 20 conexiones en modo transaction. Para 32 cores: 80 conexiones.

-- pgbouncer.ini pool_size = 20 -- para 8 cores reserve_pool_size = 5 -- conexiones extra para picos

Más conexiones no significa más velocidad. De hecho, cuando todas las conexiones activas saturan los CPUs, agregar más conexiones empeora el rendimiento por context switching excesivo. Menos conexiones = menos contención = más throughput.

⚠ El mito de "más conexiones = más rápido" es falso en PostgreSQL. 2.5 × cores es la regla de oro

Configuración de PgBouncer

PgBouncer se configura con pgbouncer.ini y un archivo de usuarios (userlist.txt). Escucha en un puerto diferente al de PostgreSQL y los clientes se conectan a él.

[databases] mydb = host=127.0.0.1 port=5432 dbname=mydb [pgbouncer] listen_port = 6432 pool_mode = transaction max_client_conn = 500 default_pool_size = 20

PgBouncer se instala vía apt (apt install pgbouncer) o desde fuente. No requiere cambios en PostgreSQL. Los clientes solo cambian el puerto de conexión de 5432 a 6432. PgBouncer tiene su propio log y monitoreo vía SHOW commands.

⚠ Si PgBouncer falla, todos los clientes pierden conexión. Pon un proxy como HAProxy delante para alta disponibilidad

Monitoreo de PgBouncer

PgBouncer expone métricas vía comandos SHOW mientras estás conectado a su base de datos administrativa (pgbouncer). También se integra con Prometheus via pgbouncer_exporter.

SHOW POOLS; -- conexiones por pool SHOW STATS; -- consultas por segundo, bytes transferidos SHOW CLIENTS; -- clientes conectados al pool

Las métricas clave: avg_recv, avg_sent (bytes promedio), total_query_time (tiempo total de consultas), avg_query_time (tiempo promedio). Si avg_wait_time es alto, el pool size es insuficiente. Si la cola de clientes crece, aumenta max_client_conn.

⚠ avg_wait_time > 10ms indica que los clientes están esperando por conexiones libres. Aumenta pool_size si hay CPUs libres

Ejemplo paso a paso

1

Instalamos PgBouncer y creamos la configuración básica:

# Instalación sudo apt install pgbouncer # /etc/pgbouncer/pgbouncer.ini [databases] mydb = host=127.0.0.1 port=5432 dbname=mydb [pgbouncer] listen_port = 6432 pool_mode = transaction default_pool_size = 20
2

Creamos el archivo de usuarios (userlist.txt con contraseñas en texto plano o SCRAM):

# /etc/pgbouncer/userlist.txt "admin" "password123" "app_user" "app_pass456"
3

Iniciamos PgBouncer y verificamos que escuche:

sudo systemctl start pgbouncer sudo systemctl status pgbouncer netstat -tlnp | grep 6432 -- debe mostrar PgBouncer escuchando
4

Los clientes se conectan al puerto 6432 en vez de 5432:

psql -h localhost -p 6432 -U app_user -d mydb -- La aplicación ve la misma base de datos, pero PgBouncer gestiona las conexiones internas
5

Monitoreamos el pool desde la consola administrativa:

psql -h localhost -p 6432 -U admin -d pgbouncer pgbouncer=# SHOW POOLS; pgbouncer=# SHOW STATS;

Resumen del módulo

  • PostgreSQL no escala bien con >200 conexiones. Cada conexión = proceso del sistema
  • PgBouncer pooliza conexiones: un pool pequeño de conexiones reales reasignadas entre clientes
  • Transaction pooling: asigna conexión solo durante una transacción. Escala hasta miles de clientes
  • Session pooling: mantiene la conexión por sesión. Más simple pero menos escalable
  • Pool size óptimo = 2.5 × cores (IO-bound) o cores + 1 (CPU-bound)
  • Monitorea avg_wait_time para detectar si necesitas más conexiones en el pool
