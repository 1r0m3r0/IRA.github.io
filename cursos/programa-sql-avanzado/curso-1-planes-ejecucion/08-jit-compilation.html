🔥 JIT Compilation

Compilación Just-In-Time para acelerar expresiones complejas

💡 Piénsalo así: JIT es como tener un traductor humano en vez de leer un libro de frases cada vez que hablas. En vez de interpretar la expresión SQL línea por línea cada vez (como un intérprete), JIT la compila a código máquina una sola vez y luego la ejecuta a velocidad nativa. El truco: si la consulta es muy corta, el tiempo de "traducción" no compensa.

LLVM JIT

PostgreSQL usa LLVM (Low Level Virtual Machine) para compilar expresiones SQL a código máquina nativo. Las expresiones en WHERE, SELECT, y JOIN conditions se traducen a IR (intermediate representation) de LLVM, que luego se optimiza y compila a código máquina.

jit = on -- habilitado por defecto desde PG11 jit_provider = llvmjit -- proveedor LLVM

JIT compila tres cosas: (1) Expressions: funciones como date_trunc, extract, CASE; (2) Tuple deforming: descomprimir tuplas del formato de almacenamiento a columnas; (3) Qual checks: evaluar condiciones WHERE. La compilación ocurre una vez; la ejecución compilada se reusa para todas las filas.

⚠ JIT requiere que LLVM esté instalado (--with-llvm en compilación). Sin LLVM, JIT no funciona

jit_above_cost

Umbral de costo para activar JIT. Por defecto: 100000 (equivalente a ~100,000 filas estimadas). Si el plan de ejecución estima un costo total mayor a jit_above_cost, PostgreSQL considera JIT.

jit_above_cost = 100000 -- default jit_optimize_above_cost = 500000 -- optimización más agresiva

Incluso si jit_above_cost se supera, JIT solo se activa si el beneficio estimado supera el overhead de compilación. PostgreSQL compara el costo de ejecución interpretada vs compilada. Para consultas OLTP (costo < 1000), JIT nunca se activa porque el overhead de compilación es mayor.

⚠ Bajar jit_above_cost a 10000 puede hacer que consultas OLTP se vuelvan más lentas por el overhead de compilación

Tuple Deforming

Cuando PostgreSQL lee una tupla del disco, está en formato de almacenamiento (binario comprimido). "Deformarla" significa convertirla a columnas individuales en memoria. JIT acelera este proceso generando código especializado para la estructura exacta de la tabla.

-- Sin JIT: tuple deforming genérico para cualquier tabla -- Con JIT: código máquina específico para las columnas de esta tabla

El tuple deforming puede consumir hasta el 30% del tiempo de CPU en consultas que leen muchas filas. JIT reduce este tiempo generando código que deserializa solo las columnas necesarias, en el orden correcto, sin condicionales.

⚠ El beneficio de JIT en tuple deforming es mayor en tablas con muchas columnas (>20) y consultas que seleccionan pocas

Inlining de funciones

JIT también inlinea (expande en línea) funciones pequeñas como coalesce, NULLIF, o funciones PL/pgSQL simples. En vez de llamar a la función (con overhead de llamada), el código se inserta directamente en la expresión compilada.

SELECT coalesce(monto, 0) + iva FROM facturas;

Sin JIT, coalesce se ejecuta como una llamada a función con overhead. Con JIT, coalesce se inlinea: una instrucción cmp + cmov (x86) reemplaza toda la llamada. La ganancia es mayor cuando hay muchas funciones pequeñas en el SELECT o WHERE.

⚠ Las funciones PL/pgSQL complejas no se inlinean. Solo funciones SQL simples y expresiones booleanas se benefician

Debugging JIT

PostgreSQL provee herramientas para diagnosticar si JIT está funcionando. EXPLAIN (ANALYZE, SUMMARY) muestra el tiempo de JIT. pg_stat_jit muestra estadísticas acumuladas.

EXPLAIN (ANALYZE, SUMMARY, TIMING OFF) SELECT count(*) FROM large_table; -- Busca: "JIT: functions: 3, options: Inlining, Optimization, Expressions"

Las líneas en EXPLAIN que empiezan con "JIT:" indican que JIT se activó. Si no ves esa línea, JIT no se usó (por bajo costo o porque LLVM no está disponible). pg_stat_jit muestra el total de funciones compiladas y el tiempo invertido.

⚠ JIT puede reportarse como activo pero con bajo impacto. Verifica el tiempo de JIT vs. tiempo total de ejecución

Ejemplo paso a paso

1

Verificamos si JIT está disponible en nuestra instalación:

SHOW jit; -- debe ser 'on' -- Si el binario se compiló con --with-llvm, JIT está disponible
2

Ejecutamos una consulta pesada que active JIT:

EXPLAIN (ANALYZE, SUMMARY, COSTS OFF) SELECT count(*) FROM generate_series(1,10000000) n WHERE n % 2 = 0 AND n % 3 = 0 AND n % 5 = 0;
3

Buscamos en la salida el bloque JIT:

JIT: Functions: 4 Options: Inlining false, Optimization false, Expressions true, Deforming true Timing: 12.345 ms (compilation), 8.456 ms (execution)
4

Comparamos con y sin JIT para medir el beneficio real:

SET jit = off; -- Ejecutar la misma consulta y comparar tiempos
5

Si JIT no ayuda (consulta OLTP), lo desactivamos para esa sesión:

SET jit = off; -- desactiva JIT completamente -- O más selectivo: SET jit_above_cost = 10000000; -- solo para consultas extremadamente pesadas

¿Cuándo conviene JIT?

Bueno para JIT

Consultas largas, muchas filas, funciones complejas, WHERE con muchas condiciones, SUM/CASE complejos.

Malo para JIT

Consultas cortas (<1s), OLTP, joins simples, pocas filas. El overhead de compilación no se recupera.

Resumen del módulo

  • JIT compila expresiones SQL a código máquina via LLVM para acelerar consultas pesadas
  • Se activa automáticamente cuando el costo estimado > jit_above_cost (default 100000)
  • Compila tres áreas: expressions, tuple deforming, qual checks
  • El overhead de compilación (~10-30ms) solo se recupera en consultas largas con muchas filas
  • Para OLTP, JIT casi nunca se activa (y cuando lo hace, empeora el rendimiento)
  • EXPLAIN (ANALYZE, SUMMARY) muestra si JIT se activó y su impacto en tiempo
