🔗 Nested / Hash / Merge Join

Las tres estrategias de join que PostgreSQL puede elegir

💡 Piénsalo así: Los joins son como organizar una cena: Nested Loop es invitar a cada amigo de uno en uno a la mesa (muchas visitas a la nevera). Hash Join es preparar una tabla con todos los ingredientes antes de cocinar. Merge Join es ordenar dos mazos de cartas y mezclarlos ordenadamente.

  • Cómo la complejidad computacional O(N×M) vs O(N+M) afecta el rendimiento
  • A identificar el mejor join para cada escenario de consulta

Nested Loop Join

Para cada fila de la tabla externa, busca coincidencias en la interna usando un índice. Ideal cuando una tabla es muy pequeña (1-100 filas) y la otra tiene un índice eficiente.

Nested Loop (cost=0.29..12.50 rows=1 width=80) -> Index Scan using pk on usuarios -> Index Scan on pedidos

Complejidad O(N × log M) con índice, O(N × M) sin índice. PostgreSQL solo lo elige cuando N es pequeño (típicamente < 1000 filas externas). El startup cost es bajo porque la primera fila llega rápido.

⚠ Sin índice en la tabla interna, Nested Loop puede ser 1000× más lento que Hash Join

Hash Join

Construye una tabla hash en memoria con la tabla más pequeña y escanea la grande una sola vez. Es el join más versátil y el que PostgreSQL elige por defecto cuando no hay índices.

Hash Join (cost=45.00..234.00 rows=5000 width=40) Hash Cond: (p.cliente_id = c.id) -> Seq Scan on pedidos -> Hash -> Seq Scan on clientes

La tabla clientes (500 filas) cabe en work_mem y se convierte en hash table. Luego se escanean pedidos (10,000 filas) una vez. Complejidad O(N+M), excelente para tablas medianas.

⚠ Si la hash table no cabe en work_mem, PostgreSQL derrama a disco en múltiples batches, degradando el rendimiento

Merge Join

Fusiona dos conjuntos ordenados escaneando ambos simultáneamente. Como una cremallera: avanza por ambas listas comparando claves. Muy eficiente para datos pre-ordenados.

Merge Join (cost=234.00..567.00 rows=50000 width=40) Merge Cond: (a.id = b.id) -> Sort -> Seq Scan on tabla_a -> Sort -> Seq Scan on tabla_b

Si las tablas ya están ordenadas por un índice, el Sort se elimina y el Merge Join es imbatible. Sin orden previo, el Sort cuesta O(N log N) y puede ser más caro que Hash Join.

⚠ Merge Join sin índices requiere ordenar ambas tablas. Si no caben en work_mem, usa disco y se vuelve lento

Memoize

Técnica nueva (PostgreSQL 14+) que cachea resultados de subconsultas correlacionadas. Si el mismo valor se repite, PostgreSQL usa el cache en vez de re-ejecutar.

Nested Loop (cost=...) -> Seq Scan on usuarios -> Memoize -> Index Scan on pedidos

Memoize almacena pares (clave → resultado). Si un usuario tiene 10 pedidos, el primer pedido va al índice, los 9 siguientes salen del cache. Reduce drásticamente el tiempo para valores repetidos.

⚠ Memoize solo funciona cuando hay valores duplicados en el lado externo del join

Ejemplo paso a paso

1

Creamos dos tablas relacionadas: clientes (500 filas) y pedidos (50,000 filas)

CREATE TABLE clientes (id SERIAL PRIMARY KEY, nombre TEXT); CREATE TABLE pedidos (id SERIAL PRIMARY KEY, cliente_id INT REFERENCES clientes(id), total NUMERIC);
2

Ejecutamos EXPLAIN para un JOIN simple sin índices en la FK

EXPLAIN SELECT * FROM clientes c JOIN pedidos p ON c.id = p.cliente_id;
3

PostgreSQL elige Hash Join: clientes (500 filas) como build, pedidos (50,000) como probe

Hash Join (cost=16.50..2450.00 rows=50000 width=80) Hash Cond: (p.cliente_id = c.id) -> Seq Scan on pedidos (cost=0.00..1240.00 rows=50000 width=40) -> Hash (cost=8.50..8.50 rows=500 width=40) -> Seq Scan on clientes (cost=0.00..8.50 rows=500 width=40)
4

Si creamos un índice en pedidos(cliente_id), el plan cambia drásticamente

CREATE INDEX ON pedidos(cliente_id); EXPLAIN SELECT * FROM clientes c JOIN pedidos p ON c.id = p.cliente_id WHERE c.id = 1; -- Ahora usa Nested Loop con el índice: solo busca los pedidos del cliente 1
5

Para consultas analíticas que ordenan por fecha, Merge Join puede ser el rey

EXPLAIN SELECT * FROM clientes c JOIN pedidos p ON c.id = p.cliente_id ORDER BY c.id; -- Si ambos tienen índices ordenados, Merge Join evita el Sort explícito

Resumen del módulo

  • Nested Loop: ideal cuando una tabla es pequeña y la otra tiene índice. Startup rápido, primera fila inmediata
  • Hash Join: construye tabla hash en memoria. Versátil y eficiente para tablas medianas sin índices
  • Merge Join: fusiona datos ordenados. Excelente para rangos grandes si los datos ya están ordenados
  • La presencia de índices cambia drásticamente qué join elige el optimizador
  • work_mem es crítico para Hash Join y Merge Join: si no cabe, derrama a disco
  • Memoize (PG14+) cachea subconsultas correlacionadas para valores repetidos
