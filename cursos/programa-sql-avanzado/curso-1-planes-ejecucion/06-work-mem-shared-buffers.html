💾 work_mem / shared_buffers

Ajusta la memoria de PostgreSQL como un cirujano

💡 Piénsalo así: shared_buffers es como el mostrador de tu cocina: el espacio donde pones los ingredientes para trabajar. work_mem es como la licuadora: más grande permite procesar más cosas a la vez, pero si la llenas demasiado, se desborda (swap). La RAM total es tu cocina completa.

🎯 ¿Qué aprenderás?

  • Comprender el concepto fundamental de SQL explicado en este módulo
  • Aplicar la sintaxis correcta con ejemplos prácticos de consultas
  • Evitar errores comunes y optimizar el rendimiento
  • Desarrollar intuición para elegir la técnica adecuada

¿Qué aprenderás?

  • La diferencia entre shared_buffers, work_mem, effective_cache_size y maintenance_work_mem
  • Cómo calcular los valores óptimos según la RAM disponible

  • La relación entre shared_buffers y el cache del sistema operativo
  • Cómo diagnosticar memoria insuficiente con EXPLAIN (Hash Batches, Sort溢出)

shared_buffers

Memoria compartida donde PostgreSQL cachea páginas de datos. Reduce lecturas de disco. Valor típico: 25% de la RAM total. No más de 8-10 GB en Windows (limitación del sistema operativo).

shared_buffers = 2GB -- para un servidor con 8GB RAM

PostgreSQL usa shared_buffers para almacenar páginas recién leídas o modificadas. El sistema operativo también cachea archivos (page cache). La suma de ambos es el cache total efectivo (effective_cache_size).

⚠ En Linux, shared_buffers por encima de 8GB puede causar contención de buffers. En Windows, el límite es más restrictivo.

work_mem

Memoria disponible para operaciones internas: ordenamientos (Sort), hash tables (Hash Join), agregaciones. Se asigna por operación, no por sesión. Una consulta con 3 sorts usa 3 × work_mem.

work_mem = 64MB -- 64 MB por operación de sort/hash

Si work_mem es insuficiente, PostgreSQL derrama a disco (temp files). EXPLAIN muestra "Sort Method: external merge Disk: 248kB" cuando hay spill. En servidores con múltiples conexiones, work_mem alto multiplica el riesgo de agotar RAM.

⚠ 100 conexiones × 64MB work_mem × 3 sorts = 19.2 GB potenciales. ¡Ajusta con cuidado!

effective_cache_size

Estimación del cache total disponible para PostgreSQL: shared_buffers + page cache del OS. No reserva memoria, solo informa al optimizador para que estime el costo de accesos a disco.

effective_cache_size = 6GB -- para 8GB RAM total

El optimizador usa este valor para decidir si un Index Scan es mejor que Seq Scan. Si el índice está cacheado, el acceso es más barato. Un effective_cache_size alto favorece el uso de índices. Un valor bajo favorece Seq Scans.

⚠ effective_cache_size demasiado alto hace que PostgreSQL sobrestime la efectividad del cache y subestime costos de IO

maintenance_work_mem

Memoria para operaciones de mantenimiento: VACUUM, CREATE INDEX, REINDEX, ADD FOREIGN KEY. Al ser operaciones únicas (no concurrentes), puede ser mucho mayor que work_mem.

maintenance_work_mem = 1GB -- VACUUM y CREATE INDEX más rápidos

Un VACUUM con maintenance_work_mem pequeño lee las páginas muertas varias veces. Con memoria suficiente, VACUUM procesa más páginas por pasada. CREATE INDEX también usa esta memoria para construir el árbol B+ en memoria.

⚠ En réplicas, maintenance_work_mem alto no afecta tanto, pero en primarios con mucha actividad, puede competir con work_mem

wal_buffers

Memoria para buffers de Write-Ahead Log (WAL). Los cambios se escriben primero en WAL, luego en disco. wal_buffers = -1 (auto) lo ajusta a ~3% de shared_buffers, mínimo 64KB.

wal_buffers = 16MB -- típico para servidores transaccionales

WAL buffers absorben escrituras pequeñas antes de volcarse a disco. Si son muy pequeños, PostgreSQL escribe WAL constantemente, aumentando IOPS. Si son muy grandes, hay riesgo de pérdida de datos en crash.

⚠ wal_buffers excesivo (>64MB) desperdicia memoria. El valor por defecto (-1) funciona bien en la mayoría de casos

Autovacuum

Proceso automático que ejecuta VACUUM y ANALYZE. Configurado por autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0.2). Se activa cuando el 20% de las filas han cambiado.

autovacuum_vacuum_scale_factor = 0.1 -- más agresivo, ideal para OLTP

Autovacuum evita el bloat excesivo. Si no corre con suficiente frecuencia, las tablas crecen desmesuradamente y los planes de ejecución se degradan. En tablas muy grandes, la escala factor puede causar que autovacuum casi nunca se active.

⚠ En tablas de 100M filas, scale_factor 0.2 significa esperar 20M cambios. Mejor usar autovacuum_vacuum_threshold fijo

Ejemplo paso a paso

1

Configuración para un servidor PostgreSQL con 16 GB de RAM dedicado:

shared_buffers = 4GB -- 25% de 16GB effective_cache_size = 12GB -- 75% de 16GB work_mem = 64MB -- 16GB / (max_connections × 2.5) maintenance_work_mem = 1GB -- operaciones de maint.
2

Verifica si work_mem es suficiente. Ejecuta EXPLAIN ANALYZE y busca "Sort Method: external merge":

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM ventas ORDER BY monto DESC; -- Si ves "external merge Disk", work_mem es insuficiente. Auméntalo.
3

Monitorea el hit ratio de shared_buffers:

SELECT 'hit ratio' as metric, sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) * 100 FROM pg_statio_user_tables; -- Ideal: >99%. Si es menor, aumenta shared_buffers
4

Detecta si autovacuum está al día:

SELECT relname, n_dead_tup, n_live_tup, round(n_dead_tup * 100.0 / n_live_tup, 1) AS dead_pct FROM pg_stat_user_tables WHERE n_live_tup > 0 ORDER BY dead_pct DESC LIMIT 10;
5

Verifica el uso de temp files por consultas con work_mem insuficiente:

SELECT query, temp_blks_written FROM pg_stat_statements ORDER BY temp_blks_written DESC LIMIT 10; -- Consultas con muchos bloques temporales necesitan más work_mem

Resumen del módulo

  • shared_buffers: cachea páginas de datos. 25% RAM. Máximo 8-10 GB
  • work_mem: para sorts y hash tables. Peligroso si es muy alto con muchas conexiones
  • effective_cache_size: estimación del cache total. Afecta la decisión entre Seq Scan e Index Scan
  • maintenance_work_mem: para VACUUM y CREATE INDEX. Puede ser más alto por ser operaciones únicas
  • Monitorea Sort Method: external merge para detectar work_mem insuficiente
  • Monitor de hit ratio (>99%) y temp files para diagnosticar cuellos de botella de memoria
